# Thinkpad Trackpoint Keyboard II (KC-1957) 固件 MOD

对 **Thinkpad Trackpoint Keyboard II（KC-1957，MCU = nRF52832）** 键盘主板固件所做的两项独立改造，以及从原始固件到最终产物的完整工程记录。

本仓库提供**改造说明文档、可复现的补丁脚本、独立的验证脚本**；**不包含**原厂固件二进制与改造后固件二进制（见 [为什么不提供 .bin](#十三为什么不提供-bin)）。

## 一、这是什么

KC-1957 是一块采用 **nRF52832** 的 Trackpoint 键盘主板，主 Flash 512 KB（`0x00000000`–`0x0007FFFF`），另有一块 4 KB 的 UICR 配置区（`0x10001000`–`0x10001FFF`）。

固件本身没有开源，本项目的一切工作都建立在**静态逆向**之上：从 J-Link 读回的原始固件二进制出发，用 Keystone 汇编器生成 Thumb 指令、用 Capstone 反汇编器逐字节复核，并通过自研的最小 Thumb 解释器（`thumbsim.py`）做行为仿真。

**关键约束：所有结论均来自静态分析与仿真，尚未经过实机刷写验证。** 使用前请务必阅读 [第十二节](#十二已知限制与风险)。

## 二、两项改造

两项改造彼此**独立**，可单独使用，也可叠加。

### 改造 A：Fn 键矩阵化（v5.1）

**动因**：适配 **SL410K 盘体**。该盘体的 Fn 键不再以独立 GPIO（P0.6）形式提供，而必须由键盘矩阵承载。

**做法**：把原本空置的矩阵槽位 `row12 × col4`（A/S/D 所在列）定义为「虚拟 Fn 键」，Fn 判定改为 **「P0.6 拉低 **或** 矩阵 r12c4 按下」的并联**。

| | 改造前 | 改造后 |
|---|---|---|
| P0.6 GPIO（低有效） | Fn | Fn（保留） |
| 矩阵 r12c4（原空槽） | 空槽 | **虚拟 Fn**（与 P0.6 并联） |

新增内存变量仅 1 字节锁存 `FN_MATRIX @ 0x20004800`，不改动任何其它判定逻辑。对**原有**键盘（仅 P0.6）保持 100% 兼容。

> v5.1 相对 v5.0 的修订：在做 v6 时逐条复核扫描路径，发现 v5.0 的 Trampoline B（2.4G 行循环）有两处实质缺陷 —— ① 2.4G 逐位测试实际读的是寄存器 `r0` 而非 `local_84[row]`，导致 2.4G 模式下 r12c4 根本没被屏蔽；② `cmp/tst/movs` 改写 NZCV，破坏了 `0x4125E` 的 `beq` 对 Z 位的依赖，导致**第 12 行其它按键被整行丢弃**。v5.1 已逐项修正并附反例对照测试。

### 改造 B：左 Ctrl 与 Fn 完全互换（v6 → v7 → v8）

**动因**：满足部分用户对键位布局的使用习惯需求。

| 物理位置 | 改造前 | 改造后 |
|---|---|---|
| 矩阵 r15c0（原 Left Ctrl 键位） | 发 Left Ctrl | **充当 Fn**（激活 Fn 层，本身不发码） |
| 矩阵 r12c4（原空槽） | 空槽 | **发 Left Ctrl**（`0xE0` 修饰位） |
| GPIO P0.6（原 Fn 键位，低有效） | Fn | **发 Left Ctrl**（经去抖） |

**核心手法**：把 `E0F`（Fn 按下状态）的**来源**整体换成为「矩阵 r15c0 按下」—— 只需隔离唯一写它的那几处去抖状态机引用，其余全部读取点自动跟随，连 `2109 = E0F && D7B`（Fn 层激活）也会自动变成跟手矩阵键。

三个版本依次解决三个问题：

| 版本 | 解决的问题 |
|---|---|
| **v6** | 键位互换本体 |
| **v7** | P0.6 判定改用**去抖后**的状态 `E0F2`，消除机械抖动导致的 Left Ctrl 误触发 |
| **v8** | 消除 2.4G 路径对 Fn 状态**滞后一个扫描周期**的固有现象（与 BT 路径对齐） |

## 六、怎么用

> **前置**：先按 [`KC-1957_固件Dump与刷回操作说明.md`](Trackpoint%20Keyboard%20II%20%28KC-1957%29/KC-1957_固件Dump与刷回操作说明.md) 把主板原始固件完整 Dump 出来，得到 **512 KB** 的主 Flash 文件（`0x00000000`–`0x0007FFFF`）。
>
> 下文用 `KC-1957_88_orig.bin` 指代这个文件 —— 改名不影响脚本运行。

> ⚠️ **必须使用 V2 及以上版本的硬件 Dump 出来的固件。** V1 等低版本硬件的固件布局与本项目所依据的版本不同，补丁的注入地址与键位表假设不成立。**若你的设备是低版本，本仓库的补丁不适用**，需要自行向持有 V2+ 设备固件的人索取一份 V2+ 固件再来打补丁。详见 [第十节](#十硬件版本要求v2-及以上)。

> ⚠️ **不要用哈希校验判断固件对不对。** 每台设备 Dump 出来的固件**本来就不完全一样**（蓝牙名称、2.4G 无线 ID 等为设备独有内容），因此原厂固件与改造后固件的 SHA-256 **都因机而异**，不能作为校验依据。**唯一可靠的判据是补丁工具的前置检查与验证脚本的结构性检查**，详见 [第十一节](#十一如何判断补丁是否正确不要用哈希校验)。

### 6.1 通用流程

```bash
# 1) 干跑：只做检查与报告，不写盘
python <补丁脚本>.py KC-1957_88_orig.bin

# 2) 正式打补丁 —— --out 必须显式指定
python <补丁脚本>.py KC-1957_88_orig.bin --out KC-1957_88_<版本>.bin --apply

# 3) 独立验证
python <验证脚本>.py KC-1957_88_orig.bin KC-1957_88_<版本>.bin
```

> ⚠️ **`--out` 必须显式指定。** 所有补丁脚本在未给 `--out` 时会回退到输入路径，一旦带上 `--apply` 就会**覆盖你的原始固件**。脚本会先写一份 `.bak` 备份，但请不要依赖它。

### 6.2 改造 A（v5.1）

```bash
cd "Trackpoint Keyboard II (KC-1957)/Fn Matrix Patch (SL410K)"

python fn_matrix_patch3.py KC-1957_88_orig.bin --out KC-1957_88_fn7_v51.bin --apply
python verify_v51.py KC-1957_88_orig.bin KC-1957_88_fn7_v51.bin
```

### 6.3 改造 B —— v8（推荐）

```bash
cd "Trackpoint Keyboard II (KC-1957)/Fn&Ctrl Swap"

python fn_swap_debounce_inline_patch.py KC-1957_88_orig.bin --out KC-1957_88_v8.bin --apply

# verify_v8.py 使用命名参数
python verify_v8.py --orig KC-1957_88_orig.bin --v8 KC-1957_88_v8.bin
```

> `verify_v8.py` 的 `--orig` / `--v8` 默认值指向仓库外的本地路径，**在克隆下来的仓库中不适用**，请显式指定。

### 6.4 改造 B —— v6 / v7

```bash
cd "Trackpoint Keyboard II (KC-1957)/Fn&Ctrl Swap/v6"
python fn_swap_patch.py KC-1957_88_orig.bin --out KC-1957_88_v6.bin --apply
python verify_v6.py KC-1957_88_orig.bin KC-1957_88_v6.bin

cd ../v7
python fn_swap_debounce_patch.py KC-1957_88_orig.bin --out KC-1957_88_v7.bin --apply
python verify_v7.py KC-1957_88_orig.bin KC-1957_88_v7.bin
```

### 6.5 校验文件完整性

```bash
cd "Trackpoint Keyboard II (KC-1957)/Fn&Ctrl Swap/v6"
sha256sum -c SHA256SUMS.txt
```

> - `*.bin` 条目指向**未随仓库发布**的固件，校验时报 `No such file or directory` —— 属正常。
> - 这些 `.bin` 哈希是**参考机**的产物指纹。**你在自己设备上生成的产物哈希不会相同**（原厂固件本就因机而异），因此**不要**用它们判断补丁是否正确 —— 判据见 [第十一节](#十一如何判断补丁是否正确不要用哈希校验)。
> - 文档与脚本条目可正常校验，用于确认仓库文件未被篡改。

## 八、刷机流程

完整步骤见 [`KC-1957_固件Dump与刷回操作说明.md`](Trackpoint%20Keyboard%20II%20%28KC-1957%29/KC-1957_固件Dump与刷回操作说明.md)。要点：

1. **硬件**：SEGGER **J-Link OB** + 测试夹，SWD 三线（GND / SWDIO / SWDCK）。
   - **VTref 悬空，不要接 5V**（接错会烧 J-Link OB 与主板）。
   - **读写时键盘必须上电**，断电状态下 J-Flash 连不上芯片。
2. **Dump**：J-Flash 配置 `nRF52832_xxAA` + `SWD`，执行 `Target → Manual Programming… → Read Back → Full chip…`，分别保存主 Flash（512 KB）与 UICR（4 KB）。
   - 可以顺手记一下 SHA-256，但它**只用于确认自己重复 Dump 的结果是否稳定**，不能用来判断固件对不对（见 [第十一节](#十一如何判断补丁是否正确不要用哈希校验)）。
3. **刷回顺序不可颠倒**：
   1. `Erase`（整片擦除主 Flash 与 UICR）
   2. `Program` 主 Flash（起始地址 `0x00000000`）
   3. `Program` UICR（起始地址 `0x10001000`）—— **这 4 KB 不能漏写**
   4. `Verify`（或直接用 `Program & Verify`，看到 `Verified OK`）
4. **务必先完整备份再动手** —— Dump 出来的两个文件是唯一的救砖手段。

## 九、为什么可以相信这些补丁

补丁不是拍脑袋写的，每一步都有可复核的证据：

| 环节 | 手段 |
|---|---|
| 定位注入点 | Capstone 逐条反汇编，对钩子点、代码空洞、字面量池做穷举核对 |
| 生成指令 | Keystone 汇编，**逐字节**与目标地址比对 |
| 行为正确性 | 自研最小 Thumb 解释器（`thumbsim.py`）执行补丁后的 trampoline，仿真输出 |
| 改动范围 | 与原始固件做**逐字节 diff**，确认改动只落在预期区间，其余 524 KB 完全一致 |
| 空洞安全 | 注入区 `0x50000`–`0x504FF` 必须全为 `0xFF` 且静态不可达，否则**硬中止** |
| 自洽性 | 补丁脚本启动时做语义自检（如「蓝牙行掩码 row15 的 bit0 必须放行 col0，否则 Fn 永不触发」） |
| 反例对照 | 验证脚本包含**反例**用例，确保检查项真的能抓出问题，而不是恒真 |

**v8 的额外验证**：`verify_v8.py` 内含 E0F 新鲜度仿真，用 4 组用例证明行循环后的 `0x413D0 cbz r7` 读到的是**本轮最新**的 E0F（零滞后），与 BT 路径行为一致。

**v5.1 的额外验证**：包含针对 v5.0 两处缺陷的**反例对照测试** —— 即证明修正后的版本不会再犯那两个错。

## 十、硬件版本要求（V2 及以上）

> ⚠️ **本项目只适用于 V2 及以上版本的硬件。**

本项目的全部注入地址、行掩码位、键位表偏移，都是基于 **V2+ 硬件**的固件布局逆向得出的。V1 等低版本硬件的固件布局不同，这些地址与假设**不成立**，强行打补丁会得到行为不可预期甚至变砖的固件。

**如果你的设备是低版本：**

- 本仓库的补丁**不适用**，请不要尝试。
- 需要**自行向持有 V2+ 设备固件的人索取**一份 V2+ 固件（Dump 出来的 512 KB 主 Flash 文件），再基于它打补丁。
- 索取时请一并说明用途（本项目只在该固件上追加键位改造逻辑，不改动扫描/蓝牙/无线功能）。

**如何确认自己的设备是 V2+：**

最直接的办法是**直接干跑补丁**：

```bash
python fn_swap_debounce_inline_patch.py KC-1957_88_orig.bin
```

补丁脚本在真正写盘前会做一整套前置检查（键位表特征、ROWPIN 表、行掩码位、钩子代码点、代码空洞必须全 `0xFF`、E0F2 选址窗口无冲突等）。**V2+ 固件会顺利通过全部检查；V1 固件会在某一项上明确中止并说明原因。** 干跑不写盘，对固件没有任何影响，可以放心执行。

> 这是判断固件版本是否适用的**唯一可靠方式** —— 不存在「看起来是 V2」的可靠外观判据，固件版本与键盘外观并非一一对应。

## 十一、如何判断补丁是否正确（不要用哈希校验）

> ⚠️ **每台设备 Dump 出来的固件本来就不完全一样，因此固件的 SHA-256 因机而异，不能用来校验补丁是否正确。**

### 11.1 为什么哈希在这里不适用

512 KB 主 Flash 里包含**设备独有内容**，同一型号的不同键盘 Dump 出来也不一样：

| 设备独有内容 | 位置 | 说明 |
|---|---|---|
| 蓝牙设备名称 | `0x21228` | ASCII `TrackPo` 开头，后接机型/序号 |
| 2.4G 无线 ID | `0x78054`（特征 `F3 FC` 之后 12 字节） | 每台机器的无线配对 ID |

实测证据（本项目在两台"虚拟设备"上跑同一套补丁）：

| | 设备 A（参考机） | 设备 B | 能否跨设备比对 |
|---|---|---|---|
| Dump 出的原始固件 SHA-256 | `57df656c…` | `3f3ba72f…` | ❌ 不同 |
| 补丁后固件 SHA-256 | `1baaef2d…` | `2cb28a38…` | ❌ 不同 |
| **两个补丁产物的逐字节差异** | — | **仅 18 字节**，且全部落在 `0x21228`（蓝牙名称）与 `0x78054`（2.4G ID） | ✅ 改造逻辑完全一致 |

也就是说：**改造成果在任意设备上都是逐字节一致的**，变的只有设备自己的身份数据。哈希不同恰恰说明"这是你自己的机器"，而不是"补丁出了问题"。

### 11.2 正确的判据：工具的前置检查与结构性验证

**第一步 —— 补丁脚本的前置检查（干跑）**

```bash
python fn_swap_debounce_inline_patch.py KC-1957_88_orig.bin
```

干跑会做这些检查，任一不满足即**中止**并说明原因：

- 固件长度、向量表 `Reset_Handler` 不得被改动
- 键位表特征字、ROWPIN 表（行号 → GPIO 映射）必须匹配
- 蓝牙 / 2.4G 两条路径的行掩码 row15 bit0 必须放行 col0（否则 Fn 永不触发）
- 代码空洞 `0x50000`–`0x504FF` 必须全为 `0xFF` 且落在合法空洞区
- 新变量 `E0F2 @0x20004800` 选址窗口内不得有其它 RAM 引用

**第二步 —— 验证脚本的结构性检查**

```bash
python verify_v8.py --orig KC-1957_88_orig.bin --v8 KC-1957_88_v8.bin
```

这一步不看哈希，而是证明"补丁只改了该改的地方"：

- 差异区间**精确等于**预期的 18 个区间（不多、不少、位置全对）
- 其余 **524018 字节逐字节相同**（设备自己的蓝牙名称、2.4G ID 完好无损）
- 5 个钩子都正确 `bl` 到对应空洞
- 各 trampoline 反汇编语义正确（row/bit 提取、字面量池、末尾复原指令）
- 数据补丁正确（键码表、行掩码、池槽指向）
- E0F 新鲜度仿真通过

> `verify_v8.py` 输出的 SHA-256 **仅作参考打印**，不参与通过判定；哈希不同时它会明确提示"正常，每台设备 Dump 结果本就不一致"。

### 11.3 各 `SHA256SUMS.txt` 里的 `.bin` 条目怎么用

这些条目是**参考机**的产物指纹，作用是"如果你在**同一台设备**上重复 Dump 并打补丁，结果应当一致"。

- **同一台设备**重复 Dump → 哈希一致（可用于确认 Dump 是否稳定、文件是否损坏）
- **不同设备** → 哈希必然不同，**属正常现象**，不必据此怀疑补丁

校验时 `.bin` 条目报 `No such file or directory` 也属正常 —— 仓库不提供固件二进制。

## 十二、已知限制与风险

> ⚠️ **本项目所有结论均来自静态分析 + 反汇编复核 + 行为仿真，没有实机刷写验证。**

- **未做实机验证**：上机前请保留原始固件 Dump 作为回滚基线。
- **硬件版本要求**：仅适用于 **V2+** 硬件，V1 等低版本不适用（见 [第十节](#十硬件版本要求v2-及以上)）。
- **不能用哈希校验固件**：Dump 结果因机而异，判据只能是工具的前置检查与结构性验证（见 [第十一节](#十一如何判断补丁是否正确不要用哈希校验)）。
- **变体固件**：若你的键盘掩码表取值与默认不同，脚本会**中止**而不是硬改。此时用 `--force-mask` 按「实际值 + 位操作」强制修补（不会覆盖掩码表其余位）；`--force` 仅用于放行钩子代码点的硬断言。
- **固件长度**：产物必须与输入固件等长。`verify_v8.py` 额外强制要求 **512 KB**（524288 字节，与主 Flash 区段一致）；v5.1 / v6 / v7 的验证脚本只校验「长度未变」。
- **r12c4 的 Left Ctrl 只在非 Fn 层生效**：Fn 层键码表未改动，按住 Fn 再按该键走的是 Fn 层映射。
- **矩阵式 Fn 的固有 1 周期滞后**：因 Fn 判定依赖 row15（最后一行）的扫描结果，这个滞后**两条路径都存在**（v8 已让两者一致，但都没有消除）。
- **X220 排线**分同面（"R"）/ 异面（"L"）版本；盘体薄膜金手指易损，尽量避免反复拆装。
- **2.4G 接收器是另一颗芯片**（罗技 CU0008，用 CCDebugger 烧写），地址体系与 nRF52832 不同，本项目不涉及。

## 十三、为什么不提供 .bin

仓库里**没有**任何 `.bin` 固件文件，两个原因：

1. **原厂固件是他人著作权成果**，随仓库再分发存在法律风险。正确做法是使用者自行用 J-Link Dump 出来 —— 这也是本项目必须先做 [Dump](#八刷机流程) 的原因。
2. **改造后固件应从自己的原始固件现场生成**，这样补丁一定作用在自己的机器上，也避免他人误刷不匹配的固件。

各版本目录的 `SHA256SUMS.txt` 里**保留了 `.bin` 的哈希条目**，作为**参考机产物指纹**（用途见 [11.3](#113-各-sha256sumstxt-里的-bin-条目怎么用)）：

| 产物（参考机） | SHA-256 |

| v5.1 `KC-1957_88_fn7_v51.bin` | `d91ecaeb1c6e55dc03ae567a6bfe3ba7b50a70cba9e47d4b4380320993e70eef` |
| v6 `KC-1957_88_v6.bin` | `5c74b3d586c9754d2b83cb9f60869715c05bace063334027512fff7dae374375` |

## 十四、术语与地址速查

| 名称 | 含义 |
|---|---|
| `E0F` | SRAM `0x20001E0F`。原为「P0.6 去抖后 Fn 按下」标志，**v6 起复用为「矩阵 r15c0 Fn 按下」** |
| `E0F2` | SRAM `0x20004800`。v6 新建，**专供 P0.6 去抖状态机**独占使用（v7 起 P0.6 发 Left Ctrl 的判定源） |
| `FN_MATRIX` | SRAM `0x20004800`。**v5.1** 新建的 1 字节锁存（改造 A，与 v6/v7/v8 的 `E0F2` 是不同分支里的同一地址，互不冲突） |
| Trampoline | 注入到代码空洞 `0x50000`–`0x504FF`（128 KB 擦除态区，静态不可达）里的补丁代码 |
| Hook | 原固件中被改写成 `bl #<trampoline>` 的调用点 |
| 2.4G / BT | 键盘的两条独立扫描路径：无线接收器通道 与 蓝牙通道 |

**注入点一览（改造 B，v6/v7/v8 共用同一套地址）**

| Hook | 地址 | 作用 |
|---|---|---|
| A | `0x1E4E4` | BT 扫描行循环 —— 写 `E0F` |
| B | `0x41252` | 2.4G 扫描行循环 —— 写 `E0F`；**v8 额外在此刷新 `r7 = E0F`** |
| C | `0x411C6` | 2.4G P0.6 判定 —— 注入伪键 `0xE0`（Left Ctrl） |
| D | `0x1EB74` | BT 行循环内即时读 `E0F` |
| E | `0x23A76` | BT HID 修饰字节 —— 注入 Left Ctrl |

**各版本产物 SHA-256 见 [第十三节](#十三为什么不提供-bin)。**
