# KC-1957（nRF52832）左 Ctrl 与 Fn 完全互换改造说明 —— v8（E0F 读取点后置）

> 补丁脚本 `fn_swap_debounce_inline_patch.py`（v8）　独立验证脚本 `verify_v8.py`　补丁产物 `KC-1957_88_v8.bin`（270 字节 / 18 区域）
>
> **本版 = v7 + 2.4G 路径 E0F 读取点后置**。在 v7「左 Ctrl 与 Fn 完全互换 + P0.6 去抖」的基础上，把 2.4G 扫描路径里「在**行循环之前**一次性读入 E0F」的结构，改为「在**行循环之内**每个 row 刷新 E0F」，从而消除 v7 中 2.4G 路径最多滞后 1 个扫描周期的固有现象，与 BT 路径对齐。
>
> **v8 直接对原始固件打补丁**（`KC-1957_88_orig.bin`），不依赖 v5/v6/v7 的任何中间产物；BT 路径**零字节改动**。
>
> 型号说明：产品型号是 **KC-1957**；固件文件名中的 `_88_` 是 88 布局代号，与型号无关。MCU 为 **nRF52832**。

## 一、最终结果和逻辑

### 1.1　用户可见的键位行为（与 v6/v7 完全一致，v8 不改变任何键位语义）

| 物理键位 | 行为 | 说明 |
|---|---|---|
| 矩阵 `r12c4`（idx 100） | 发 **Left Ctrl**（`0xE0`） | v5 起作为 SL410K 盘体的 Fn 承载槽，v6 起改发 Left Ctrl |
| 矩阵 `r15c0`（idx 120） | 充当 **Fn**（本身不产生独立键码） | v6 起最左下角 Left Ctrl 改当 Fn |
| GPIO `P0.6` | 发 **Left Ctrl**（`0xE0`），**走去抖** | v7 起读去抖后 E0F2，v8 不变 |

### 1.2　v8 改变的（唯一的）行为差异

| 路径 | v7 | v8 |
|---|---|---|
| BT（蓝牙） | E0F 在**使用点**即时读取，**无滞后** | **完全不变**（零字节改动） |
| 2.4G | E0F 在**行循环前**读入 `r7`，被循环内 `0x41286` 与循环后 `0x413D0` 消费 → **滞后 1 个扫描周期** | E0F 在**行循环内**每个 row 刷新 `r7`，循环后的 `0x413D0` 读到**本轮最新** → **零滞后** |

> 也就是说：**v8 不改变任何一个按键的输出，只把 2.4G 通道对 Fn 状态的「取样时刻」从上一轮纠正为本轮**。

### 1.3　关键设计：只动 2.4G 的两个 trampoline

v8 的全部改动落在两处：

1. **Trampoline C（0x50200 区）**：删掉 v7 里的「读 E0F → `mov r7,r0`」两步（即把 E0F 装进 `r7` 的那一步），**只保留** P0.6 → 伪 Left Ctrl 注入（读去抖变量 E0F2）。→ 由 40 字节缩到 28 字节。
2. **Trampoline B（0x50100 区）**：在 `.restore` 处新增「`ldr.w r7,[pc]` + `ldrb r7,[r7]`」两步，即**每个 row 都把当前 E0F 重新读进 `r7`**。→ 由 64 字节增到 72 字节。

净变化 **−4 字节**（v7 = 274 字节 / 18 区域 → v8 = 270 字节 / 18 区域）。

## 二、改造背景：v7 遗留的结构性滞后

### 2.1　v7 的 2.4G 路径结构

v6 把 2.4G 的 Fn 判定源从 GPIO P0.6 换成矩阵 r15c0 之后，2.4G 扫描函数里就形成了这样一段结构（**这是 v6 引入的，v7 未改变**）：

```text
2.4G 扫描函数 FUN_00041180
  │
  ├─ HOOK_C @0x411C6 ── 一次性把 E0F 读进 r7
  │      （trampoline C 的第一段：ldr.w r0,[pc] / ldrb r0,[r0] / mov r7,r0）
  │      ※ 此刻 E0F 还是**上一轮扫描**留下的值
  │
  └─< 行循环 r4 = 0 .. 15 >
         ├─ HOOK_B @0x41252 ── 扫描到 row15 时写 E0F = 本轮结果
         ├─ 内层列循环 0x41268 .. 0x4131A
         ├─ 0x41286  cbz r7   ← 消费点 ①（行循环内）
         └─ ...
     └─ 0x413D0  cbz r7   ← 消费点 ②（行循环后）
```

**问题**：`r7` 在行循环**之前**就被冻结成了上一轮的快照，而循环内、循环后两处 `cbz r7` 全程都读这个快照。行循环后那个消费点 `0x413D0`（Fn 后置动作）本应反映「本轮刚扫完」的结果，实际拿到的是上一轮。

### 2.2　BT 路径为什么没有这个问题

BT 路径的 E0F 读取点在 **HOOK_D（0x1EB74）**，位于 BT 扫描流程内部，**紧邻其消费点**：

```text
0x1EB74   bl  #0x50300      ← HOOK_D：读 E0F 进 r2
0x1EB78   nop ×9
0x1EB8A   cbnz r2, #0x1ebbc ← 消费点：r2 == 0 表示「Fn 按下」
```

且 BT 路径的 **E0F 写入点 HOOK_A（0x1E4E4）地址在前、读取点 HOOK_D（0x1EB74）在后**，同处一次扫描流程内：

```text
0x1E4E4   bl  #0x50000      ← HOOK_A：仅当 r5 == 15 时写 E0F = 本轮结果
   …（同一轮扫描继续推进）…
0x1EB74   bl  #0x50300      ← HOOK_D：读 E0F 进 r2（此时已是本轮的值）
0x1EB8A   cbnz r2, #0x1ebbc
```

即 BT 是「**先写后读、同一轮内闭环**」，读到的就是本轮的 Fn 状态；而 2.4G 是「**先读后写、跨轮**」，读到的是上一轮。**v8 的目标就是把 2.4G 改造成与 BT 同样的「同一轮内闭环」。**

### 2.3　影响面评估

滞后对象是**修饰键状态位**（Fn 标志），不是键码本身：

- Fn 本身**不产生独立键码**（`KEYTBL[120] = 0x00`），它只决定 Fn 层（`0x20002109` = E0F && D7B）是否激活、以及 Fn 修饰位是否出现在 HID 报告里；
- 滞后 1 个扫描周期（毫秒级）通常无感知，但会带来两个实际可观察的副作用：
  1. **Fn 后置动作（`0x413D0`）比 Fn 按下晚一拍**——例如「Fn + 某键」组合中，Fn 层的展开/收起比按键本身晚一个扫描周期；
  2. **松手时多残留一拍**——Fn 刚松开时，行循环后的后置动作仍会按「Fn 还按着」执行一次。

v8 把这个残留窗口消除，同时**不引入任何新的时序风险**（见第十章）。

## 三、改造前的固件事实

### 3.1　键位矩阵与键码表

矩阵为 16 行 × 8 列，列位图低位对应 col0。改造涉及两个槽位：

| 槽位 | idx | 原始键码 | v8 之后 | 承担角色 |
|---|---|---|---|---|
| `r15c0` | 120 | `0xE0`（Left Ctrl） | `0x00` | 充当 **Fn**（不产生独立键码） |
| `r12c4` | 100 | `0x00`（空槽） | `0xE0` | 发 **Left Ctrl** |

两套键码表都要改（BT 与 2.4G 各一份）：

| 表 | 基址 | `[100]` (r12c4) | `[120]` (r15c0) |
|---|---|---|---|
| `KEYTBL_BT` | `0x2CBF0` | `0x2CC54` | `0x2CC68` |
| `KEYTBL_G` | `0x4A6FA` | `0x4A75E` | `0x4A772` |

### 3.2　行掩码必须放行 col4（r12c4）

`r12c4` 在原始固件里是**被掩码屏蔽**的空槽，改造后必须让它参与扫描：

| 路径 | 行掩码地址 | 原值 | 新值 | 极性 |
|---|---|---|---|---|
| BT row12 | `0x1E84C` | `0xE7` | `0xF7` | 高有效 → `\|= bit4` |
| 2.4G row12 | `0x4A6B2` | `0x1C` | `0x0C` | 低有效 → `&= ~bit4` |

**row15 的 bit0 不能被屏蔽**（否则 Fn 永不触发）。补丁脚本启动时现场复核：BT row15 = `0x41`（bit0 = 1）、2.4G row15 = `0xBE`（bit0 = 0），两条路径下 r15c0 都参与扫描。

### 3.3　2.4G 扫描函数的行循环结构（v8 设计的依据）

`FUN_00041180` 的行循环是**外层 r4 计行、内层逐位扫列**的两层结构：

```asm
0x411C6   bl  #0x50200        ; ← HOOK_C（在行循环【之前】：P0.6 判定 / 伪键注入）
0x411CA   nop ×7
0x411D8   movs r4, #0         ; ← 外层行计数器 r4 归零
0x411DA   ldr  r1, [pc, #0x3c8]  ; ← 外层行循环体起点（0x413C0 blo.w 回跳至此）
0x411DC   ldr  r0, [pc, #0x3c8]
0x411DE   adds r1, #0xc
0x411E0   str  r0, [r1]
0x411E2   ldr.w sl, [pc, #0x3c8]

0x41240   add  r1, sp, #0x24       ; local_84[r4]
0x41246   str.w r0, [r1, r4, lsl #2]
0x4124A   ldrb r2, [r2, r4]        ; 该行的列数据
0x4124C   bics r0, r2              ; r0 = 该行列位图
0x4124E   str.w r0, [r1, r4, lsl #2]

0x41252   bl  #0x50100        ; ← HOOK_B（行循环【内】，每个 row 都执行）
0x41256   lsl.w r1, r8, r2
0x4125A   ldr  r2, [pc, #0x354]
0x4125C   str  r1, [r2]
0x4125E   beq  #0x4133e

0x41260   movs r3, #0
0x41262   movs r2, #7
0x41264   mov.w r1, r8
0x41268   lsl.w ip, r1, r2        ; ← 内层列循环起点
0x4126C   tst.w r0, ip            ;   逐位测试 r0（v6 修正① 的由来）
0x41270   beq  #0x41318
   …
0x41286   cbz  r7, #0x412ca       ; ★ 消费点 ①（行循环内）
   …
0x4131A   bhs  #0x41268           ; ← 内层列循环回跳

0x413BC   adds r4, r4, #1
0x413BE   cmp  r4, #0x10
0x413C0   blo.w #0x411da          ; ← 外层行循环回跳（r4: 0→0xF）

0x413CC   cmp  r6, #0x10
0x413CE   bne  #0x413d2
0x413D0   cbz  r7, #0x41422       ; ★ 消费点 ②（行循环后）—— v8 的目标位置
0x413D2   ldr  r3, [pc, #0x1e4]
   …
```

#### 3.3.1　`r7` 的完整生命周期（v8 设计的关键前提）

`r7` 在 2.4G 扫描函数里的每一次赋值与每一次读取都已逐条枚举（反汇编全函数体 `0x41180`–`0x413B2`）：

| # | 地址 | 指令 | 时机 | 作用 |
|---|---|---|---|---|
| W1 | `0x41180` | `push.w {r4,r5,r6,r7,r8,sb,sl,fp,lr}` | 函数序言 | 保存被调用者保存寄存器 |
| W2 | `0x41184` | `mov.w fp, #0` | 函数序言 | **帧指针被置 0**（非标准 prologue） |
| W3 | `0x4119C` | `mov r7, fp` | 函数序言 | ⇒ **r7 初值 = 0** |
| W4 | `0x411CE` | `movs r7, #1` | HOOK_C 内，**仅当 P0.6 按下** | r7 = 1 ⇒ 「Fn 按下」 |
| W5 | `0x413AE` | `pop.w {…,r7,…,pc}` | 函数尾声 | 恢复 r7（在行循环之后，不影响消费点） |
| — | `0x41286` | `cbz r7, #0x412ca` | **行循环内** | 消费点 ① |
| — | `0x413D0` | `cbz r7, #0x41422` | **行循环后** | 消费点 ② |

原始固件的函数序言（取自 `KC-1957_88_orig.bin`）：

```asm
0x41180   2D E9 F0 4F    push.w {r4, r5, r6, r7, r8, sb, sl, fp, lr}
0x41184   4F F0 00 0B    mov.w  fp, #0             ; ★ 帧指针 = 0
0x41188   A1 B0          sub    sp, #0x84
0x4118A   D9 46          mov    sb, fp
0x41198   5D 46          mov    r5, fp
0x4119A   5E 46          mov    r6, fp
0x4119C   5F 46          mov    r7, fp             ; ★ r7 = fp = 0
   …
0x411CE   01 27          movs   r7, #1             ; 仅当 P0.6 按下
0x411D6   3D 46          mov    r5, r7
```

**由此得到原始固件中 `cbz r7` 的真实语义**：因为 `fp = 0`（W2）⇒ `r7 = 0`（W3），而只有 P0.6 按下时 `r7` 才被置 1（W4），所以

> `cbz r7` ≡ **「Fn（P0.6）未按下」** 分支。（`r7` 的取值只可能是 0 或 1。）

**v6 起**把 r7 的载体从 P0.6 换成矩阵 Fn（E0F），**分支极性保持一致**：

```text
原始固件： r7 = (P0.6 按下) ? 1 : 0     →  cbz r7 = 「P0.6 未按下」
v6 / v7：  r7 = E0F（矩阵 Fn 标志）      →  cbz r7 = 「矩阵 Fn 未按下」（E0F == 0）
v8：       r7 = E0F，每 row 刷新          →  cbz r7 = 「矩阵 Fn 未按下」（本轮最新 E0F）
```

**v8 的改动只发生在「r7 何时被重新赋值」这一项上**，不改变 r7 的语义、不改变分支极性：

| 版本 | r7 的赋值时机 | 消费点 ①/② 读到的值 |
|---|---|---|
| 原始 | 序言（=0）+ P0.6 按下时（=1） | 当轮 P0.6 状态 |
| v6 / v7 | **行循环之前**一次性（HOOK_C） | **上一轮**的矩阵 Fn 状态 |
| **v8** | **行循环之内**每 row 一次（HOOK_B） | **本轮最新**的矩阵 Fn 状态 |

> **安全性推论**：`0x4119C`（W3）位于行循环之前、`0x413AE`（W5）位于行循环之后，两者都不影响两个消费点；而行循环内 trampoline B 在 `0x41252` 执行、**早于** `0x41286`，因此即使删掉 HOOK_C 的赋值，`r7` 在两个消费点处也**始终是已定义且新鲜**的。

**三个关键事实：**

1. `r7` 在 2.4G 扫描函数内被**两处** `cbz` 消费：`0x41286`（行循环内）与 `0x413D0`（行循环后）。这是 v8 设计的全部依据——v8 的补丁脚本把这两条 `cbz r7` 的存在写成了**启动时断言**，一旦目标固件里没有它们，脚本直接中止。
2. 外层行循环 `r4` 从 0 递增到 0xF，**row15 是最后一行**。这决定了矩阵式 Fn（r15c0）的 E0F 只在最后一次迭代才被最终确定。
3. `HOOK_B` 位于**行循环内**、且**在 `0x41286` 之前**执行。v8 正是利用这一点，让 `r7` 的刷新发生在 `0x41286` 之前、`0x413D0` 之前。

### 3.4　BT 扫描函数的相关位置

| 地址 | 内容 | 与 v8 的关系 |
|---|---|---|
| `0x1E4E4` | HOOK_A：行循环内，`r5 == 15` 时写 E0F | **v8 不改** |
| `0x1EB74` | HOOK_D：读 E0F 进 `r2`，紧邻消费点 `0x1EB8A cbnz r2` | **v8 不改** |
| `0x1E4E4` < `0x1EB74` | 写入点在读取点之前，同处一次扫描流程 | BT 无滞后的结构原因 |

### 4.2　v7 → v8 的执行流对比（框图）

**v7（滞后 1 轮）**

```text
2.4G 扫描函数
  │
  ├─[HOOK_C 0x411C6]─ r7 = E0F（★上一轮扫描的快照）
  │                    └─ trampoline C: ldr/ldrb/mov r7,r0
  │
  └─< 行循环 r4 = 0..15 >
       ├─[HOOK_B 0x41252]─ r4==15 时写 E0F = 本轮结果（★但 r7 不刷新）
       ├─[0x41286 cbz r7]─ 用【旧】E0F 做 Fn 次级行为
       └─ …
    └─[0x413D0 cbz r7]─ 用【旧】E0F 做 Fn 后置动作　⚠ 滞后 1 个扫描周期
```

**v8（零滞后）**

```text
2.4G 扫描函数
  │
  └─< 行循环 r4 = 0..15 >
       ├─[HOOK_B 0x41252]─ bl 0x50100
       │     ├─ r4==15：E0F = 本轮结果
       │     ├─ r7 = E0F            ★v8：每个 row 都刷新 r7
       │     └─ 复原 ldrb.w r2,[sl,r4] / cmp r0,#0 → bx lr
       ├─[0x41286 cbz r7]─ r4<15 用上轮 / r4==15 用本轮（与 BT 同构）
       └─ …
    └─[0x413D0 cbz r7]─ 用【本轮刚扫得的当前 E0F】　✓ 零滞后，与 BT 对齐
```

### 4.3　为什么「行循环内刷新」就能消除滞后

关键在于 **row15 是外层行循环的最后一次迭代**：

- 迭代 `r4 = 15` 时，HOOK_B 先把 E0F 写成本轮结果（`E0F = 当前 row15 的 bit0`），紧接着在 `.restore` 处执行 `r7 = E0F`；
- 之后外层循环 `r4` 递增到 0x10，`blo.w` 不再跳转，退出行循环；
- 循环后的 `0x413D0 cbz r7` 读到的 `r7` 就是**本轮 row15 刚写下的值** → 与 BT 的「同一轮内写完再读」完全对称。

> **固有 1 周期说明**：矩阵式 Fn（r15c0）的 E0F 必须在扫描到 row15 时才最终确定，而 row15 排在最后一行，因此相对「GPIO 直读式 Fn（P0.6）零滞后」必然存在最多 1 个扫描周期的固有滞后。v8 消除的是「**用上一轮的值**」这个**额外**的一拍，使 2.4G 与 BT 的行为完全一致。

- 唯一落在「行循环之前、且会影响消费点」的写入，就是 v7 trampoline C 的 `mov r7,r0`；

```asm
0x1EB86   00 BF          nop
0x1EB88   00 BF          nop
0x1EB8A   BA B9          cbnz  r2, #0x1ebbc       ; ← 消费点保留
0x1EB8C   53 48          ldr    r0, [pc, #0x14c]
```

原始 16 进制：`06 20 00 BF 4F F0 A0 42 11 46 00 BF D1 F8 10 25 C2 40 02 F0 01 02 00 BF`
→ Patch 后：`31 F0 C4 FB` + `00 BF`×9（`BA B9` 与 `0x1EB8C` 之后均为段外，保留）

#### ③ Trampoline D（@0x50300，24 字节）

```asm
0x50300   DF F8 10 20    ldr.w r2, [pc, #0x10]   ; r2 ← 池 @0x50314 = E0F
0x50304   12 78          ldrb  r2, [r2]          ; r2 = E0F（矩阵 Fn）
0x50306   00 2A          cmp   r2, #0
0x50308   01 D1          bne   #0x5030e          ; E0F != 0 → .held
0x5030A   01 22          movs  r2, #1            ; E0F == 0 → r2 = 1（= 原「P0.6 未按下」语义）
0x5030C   70 47          bx    lr
0x5030E   00 22          movs  r2, #0            ; .held：Fn 按下 → r2 = 0
0x50310   70 47          bx    lr
```

字面量池：

| 地址 | 字节 | 值 | 含义 |
|---|---|---|---|
| `0x50314` | `0F 1E 00 20` | `0x20001E0F` | E0F |

语义等价性：原代码算出 `r2 = (P0.IN >> 6) & 1`，即 **P0.6 未按下 → 1、P0.6 按下 → 0**；trampoline D 算出 `r2 = (E0F == 0) ? 1 : 0`，即 **矩阵 Fn 未按下 → 1、Fn 按下 → 0**。两者极性一致，因此消费点 `0x1EB8A cbnz r2`（`r2 != 0` 即「未按下」→ 跳过 Fn 相关处理）的行为被完整保留。

> **BT 路径结构上不存在 v7 的滞后问题**：HOOK_D 在**使用点**即时读 E0F，且 E0F 的写入点 HOOK_A（`0x1E4E4`）地址在前、读取点 HOOK_D（`0x1EB74`）在后，同处一次扫描流程内 → BT 读到的就是本轮的 Fn 状态。v8 因此**不改动 BT 任何字节**。

### 6.5　Hook E：BT HID 报告组装的修饰字节清零（@0x23A76）— v8 未改

#### ① 原始代码

```asm
0x23A76   00 23          movs  r3, #0
0x23A78   0B 70          strb  r3, [r1]           ; *param_1 = 0（修饰字节清零）
0x23A7A   CB 71          strb  r3, [r1, #7]       ; ← 段外，依赖 r3 == 0
0x23A7C   00 20          movs  r0, #0
0x23A7E   1D E0          b     #0x23abc
```

#### ② Patch 后代码

```asm
0x23A76   2C F0 C3 FC    bl    #0x50400          ; ← 替换 movs+strb
0x23A7A   CB 71          strb  r3, [r1, #7]       ; ← 保留（r3 已被 trampoline 复原为 0）
0x23A7C   00 20          movs  r0, #0
0x23A7E   1D E0          b     #0x23abc
```

原始 16 进制：`00 23 0B 70` → Patch 后：`2C F0 C3 FC`

#### ③ Trampoline E（@0x50400，28 字节）

```asm
0x50400   00 23          movs  r3, #0
0x50402   0B 70          strb  r3, [r1]          ; *param_1 = 0（先清零）
0x50404   DF F8 10 00    ldr.w r0, [pc, #0x10]   ; r0 ← 池 @0x50418 = E0F2
0x50408   00 78          ldrb  r0, [r0]          ; r0 = E0F2（P0.6 去抖后）
0x5040A   01 28          cmp   r0, #1
0x5040C   01 D1          bne   #0x50412          ; 未按下 → .fin
0x5040E   01 23          movs  r3, #1
0x50410   0B 70          strb  r3, [r1]          ; *param_1 = 1（置 Left Ctrl 位）
0x50412   00 23          movs  r3, #0            ; ★复原 r3 = 0（0x23A7A 的 strb r3,[r1,#7] 依赖）
0x50414   70 47          bx    lr
```

字面量池：

| 地址 | 字节 | 值 | 含义 |
|---|---|---|---|
| `0x50418` | `00 48 00 20` | `0x20004800` | E0F2 |

> 这里是 v7 的去抖生效点：读的是 E0F2（去抖后状态）而不是原始 P0.IN，机械按键抖动不会造成 Left Ctrl 误触发。v8 未改此处。

### 7.1　逐字节差异

### 7.2　语义差异一句话总结

> **v7**：2.4G 的 `r7` = 「进入行循环那一刻的 E0F」（上一轮快照）。
> **v8**：2.4G 的 `r7` = 「当前 E0F」（每 row 刷新，row15 那次即本轮最新）。
> **BT**：始终 = 「当前 E0F」（使用点即时读）—— v8 未动。

### 9.2　E0F 新鲜度仿真（v8 的核心验证）

以**从二进制反汇编中提取**的 `row_idx = 15`、`bit = 1` 仿真整轮扫描，断言行循环后 `0x413D0` 读到的 `r7` 等于**本轮最新** E0F：

| 上轮 E0F | 本轮 row15 的 bit0 | 循环后 r7 | 期望 | 结论 |
|---|---|---|---|---|
| 0 | 1 | 1 | 1 | OK（Fn 本轮按下） |
| 1 | 0 | 0 | 0 | OK（Fn 本轮松开） |
| 0 | 0 | 0 | 0 | OK |
| 1 | 1 | 1 | 1 | OK |

→ 行循环后读到的 `r7` **始终**等于本轮最新 E0F，**零滞后**，与 BT 路径对齐。

### 9.3　补丁脚本内置的启动时自检

补丁脚本在写盘前会现场复核（不通过即中止，不产出静默失效的固件）：

1. **E0F2 选址安全**：保守扫描全固件的 RAM 变量引用，确认 `0x20004800`–`0x200048FF` 窗口内引用数为 0；
2. **HOOK_A 池槽等价性**：现场解析 HOOK_A 的 `ldr r1,[pc]` 目标槽值，确认等于 `ROWPIN(0x2CBE0)`；
3. **row15 bit0 未被屏蔽**：BT row15 = `0x41`（bit0 = 1）、2.4G row15 = `0xBE`（bit0 = 0）——两条路径下 r15c0 都参与扫描，否则「Fn 将永不触发」；
4. **★v8 专属**：确认 `0x41286`（行循环内）与 `0x413D0`（行循环后）**都**是 `cbz r7`——这是 v8 设计的前提，一旦目标固件结构不同即中止；
5. **原字节安全断言**：7 处钩子/键码表/池槽的原始字节必须逐字节吻合（`--force` 可放宽钩子项，`--force-mask` 可放宽掩码项；池槽始终为硬约束）；
6. **代码空洞校验**：5 个 trampoline 落点 `0x50000`/`0x50100`/`0x50200`/`0x50300`/`0x50400` 各 0x200 字节必须全为 `0xFF`。

## 十、已知限制与风险

### 10.0　两条使用前提（务必先看）

**① 硬件版本：必须使用 V2 及以上硬件 Dump 出来的固件。**

本补丁的注入地址、行掩码位、键位表偏移全部基于 **V2+ 硬件**的固件布局逆向得出。V1 等低版本硬件的固件布局不同，这些地址与假设**不成立**，强行打补丁会得到行为不可预期甚至变砖的固件。

- 若你的设备是**低版本**：本补丁不适用，**不要尝试**；需**自行向持有 V2+ 设备固件的人索取**一份 V2+ 固件（512 KB 主 Flash 文件）再打补丁。
- **如何确认**：直接对 Dump 出来的固件**干跑**补丁脚本（`python fn_swap_debounce_inline_patch.py <固件>`）。干跑会检查键位表特征、ROWPIN 表、行掩码位、钩子代码点、代码空洞是否全 `0xFF`、新变量选址窗口是否冲突等。**V2+ 固件会顺利通过全部检查；V1 固件会在某一项上明确中止并说明原因。** 干跑不写盘，对固件无任何影响。

**② 不要用 SHA-256 判断固件或补丁对不对。**

每台设备 Dump 出来的固件**本来就不完全一样** —— 512 KB 主 Flash 中含设备独有内容（蓝牙名称 `@0x21228`、2.4G 无线 ID `@0x78054`）。因此**原厂固件与补丁产物的 SHA-256 都因机而异**。

实测：在两台设备上跑同一套补丁，**两个补丁产物之间仅 18 字节不同，且全部落在上述设备独有数据区** —— 即**改造逻辑在任意设备上逐字节一致**，变的只有设备自己的身份数据。

**唯一可靠的判据**是本脚本的**结构性检查**（见 9.1 第 2/3 项：差异区间精确等于预期 18 段、其余 524018 字节逐字节未变）与**补丁脚本的前置检查**。`verify_v8.py` 打印的哈希**仅作参考，不参与通过判定**。


### 10.1　矩阵式 Fn 的固有 1 周期（无法消除，也不需要消除）

矩阵 r15c0 的 E0F 必须等到 row15 才最终确定，而 row15 是最后一行。因此相对「GPIO 直读式 P0.6 零滞后」，矩阵 Fn 天然存在最多 1 个扫描周期的滞后。v8 消除的是**额外的**那一拍（2.4G 用上一轮的值），而不是这一拍。

**若要求 P0.6 与矩阵 Fn 完全同拍**，只能把 Fn 改为 GPIO 直读（放弃 SL410K 盘体适配）——与 v5 的改造动因冲突，故不做。

### 10.2　2.4G 路径行循环内的 Fn 次级行为仍可能用上一轮值

`0x41286 cbz r7`（行循环内）位于**列循环**之中，r4 ∈ 0..14 时 row15 尚未扫到，E0F 还是上一轮的值。这是矩阵式 Fn 的固有性质，**BT 路径同样如此**（同一份矩阵数据、同样的 row15 依赖）。v8 做到的是让两条路径**行为一致**，而不是让行循环内也变成零滞后。

### 10.3　实机验证建议

v8 相对 v7 只改变「2.4G 通道 Fn 状态的取样时刻」，**不改变任何键码输出**。实机验证重点：

| 场景 | 预期 |
|---|---|
| 2.4G 通道下按 Fn 键，观察 HID 报告修饰位 | Fn 层激活时机比 v7 提前不超过 1 个扫描周期；不应出现「Fn 粘住」或「Fn 层不收起」 |
| 2.4G 通道下快速点按 Fn | v7 会在松手后多残留一拍 Fn 状态；v8 不应再有残留 |
| 2.4G 与 BT 通道交替使用 Fn | 两条通道的 Fn 表现应一致（v7 下 2.4G 会比 BT 慢一拍） |
| 组合键（Fn + 其它键）在 2.4G 下 | 展开/收起应更贴合按键时序 |
| BT 通道全部功能 | **应与 v7 完全一致**（v8 未改 BT 任何字节） |

> 建议先在 2.4G 通道验证；若出现异常，可直接回刷 v7（`KC-1957_88_v7.bin`，SHA-256 `3f68e61b6f24c8f763958de9fe1fa88574a12b583aa3febdecaa1094dc97cdc1`）——两版差异仅 4 字节，回退成本极低。

### 10.4　本版未做的事

- 未改动 BT 路径任何字节（无必要）；
- 未新增任何 RAM 变量、钩子或去抖逻辑（E0F2 沿用 v6 引入的现成变量）；
- 未改动 Fn 层激活计算（`0x20002109` = E0F && D7B）；
- 未做实机回归（本工程当前只有离线反汇编 + 字节级验证能力）。

## 十一、踩坑与逐步确认（正确性保障）

### 11.1　v8 排障：keystone 初始化报 `KS_ERR_ARCH`

**现象**：补丁脚本启动即 `keystone.keystone.KsError: Invalid/unsupported architecture (KS_ERR_ARCH)`。

**根因**：脚本写成 `Ks(CS_ARCH_ARM, KS_MODE_THUMB)`——`CS_ARCH_ARM` 是 **capstone** 的常量（值 **0**），而 **keystone** 里 0 是 `KS_ARCH_INVALID`，`KS_ARCH_ARM` 的值是 **1**。两个库的架构枚举不是同一套编号；`CS_MODE_THUMB` 与 `KS_MODE_THUMB` 恰好都是 16，所以 mode 参数没暴露问题、只有 arch 参数出错。

**修复**：`ks = Ks(KS_ARCH_ARM, KS_MODE_THUMB)`（用 keystone 自己导入的常量）。一行。

> 教训：跨库调用时**不能凭名字相似就混用常量**。`capstone.CS_ARCH_ARM == 0`、`keystone.KS_ARCH_ARM == 1`，`CS_MODE_THUMB == KS_MODE_THUMB == 16`。

### 11.2　验证脚本解析 capstone 反汇编的两个坑

1. **mnemonic 带 `.w` 后缀**：`ldr.w` / `tst.w` / `ldrb.w` 的 `mnemonic` 字段分别是 `'ldr.w'`、`'tst.w'`、`'ldrb.w'`，与 `'ldr'`、`'tst'` **不相等**。比较前必须先 `.replace('.w', '')`，否则所有基于 mnemonic 的判定会静默失效（表现为「提取不到 row/bit」「找不到 E0F 字面量」）。
2. **字面量池会被继续反汇编成伪指令**：trampoline 尾部的池数据（如 `0F 1E 00 20`）会被 capstone 解释成 `subs r7,r1,#0` / `movs r0,#0` 这样的“指令”。判定「代码区末尾」必须**以 `bx lr` 为界**截断，不能用「blob 总长度」当代码区长度（v8 trampoline B 总长 72 字节、代码区只有 60 字节）。

### 11.3　v8 关键设计点：为什么必须刷新「行循环内」而不是「行循环后」

一个自然的想法是「把 E0F 读取点直接放到 `0x413D0` 之前」。但那样只解决消费点②，**消费点①（`0x41286`，行循环内）就会读到未定义/陈旧的 `r7`**——因为 `r7` 在 2.4G 函数内没有其他写入点。

v8 的选择是**在行循环内逐 row 刷新 `r7`**（trampoline B 的 `.restore`），一举两得：

- 消费点①（`0x41286`）：r4 = 15 那次迭代拿到本轮值，其余行仍是上一轮（与 BT 同构，矩阵固有限制）；
- 消费点②（`0x413D0`）：循环退出时 `r7` 是 row15 那次迭代刷新的值 = **本轮最新**。

### 11.4　v8 关键设计点：为什么删除 HOOK_C 的 r7 赋值是安全的

依据（见 §3.3.1 的完整枚举）：`r7` 在 2.4G 扫描函数体内的 **3 处写入**分别是 `0x4119C`（序言 `mov r7,fp` ⇒ 初值 0）、`0x411CE`（HOOK_C 的 `movs r7,#1`）、`0x413AE`（尾声 `pop` 恢复）；**2 处消费**是 `0x41286` 与 `0x413D0` 两处 `cbz r7`。

其中序言那次在行循环之前、尾声那次在行循环之后，**唯一会影响消费点的前置写入**就是 v7 trampoline C 的 `mov r7,r0`。删除它、并把该写入挪到行循环内的 trampoline B（`0x41252`，早于 `0x41286`）之后，`r7` 在两个消费点处**始终有定义且是本轮最新值**，**不产生任何新的未定义行为**。

> 附带结论：原始固件中 `r7` 初值为 0（因 `mov.w fp,#0`），且只有 P0.6 按下时才置 1，故 `cbz r7` 的原始语义就是「**Fn（P0.6）未按下**」。v6 把载体换成矩阵 Fn 后语义自然变成「矩阵 Fn 未按下」，v7/v8 只是改变**取样时刻**，不改变语义与极性。

### 11.5　逐步确认清单

- [x] 2.4G 函数体内 `r7` 的全部写入点与消费点已枚举（**3 处写**：序言 `mov r7,fp` / HOOK_C `movs r7,#1` / 尾声 `pop`；**2 处读**：`0x41286`、`0x413D0`）；
- [x] `0x41286` / `0x413D0` 两条 `cbz r7` 已在成品固件中复核存在；

### 12.2　v8 的两处「外科式」改动

1. **Trampoline C（0x50200）**：删除「读 E0F → `mov r7,r0`」三步与随之无用的 E0F 池项。语义上，`r7` 的**写入时机**从「行循环前」移到「行循环内」。
2. **Trampoline B（0x50100）**：在 `.restore` 处新增「`ldr.w r7,[pc]` + `ldrb r7,[r7]`」两步。语义上，`r7` 的**取样频率**从「每次扫描一次」变成「每个 row 一次」。

两处改动合起来，等价于把 2.4G 路径的 Fn 标志从「**快照**」变成「**实时镜像**」，从而与 BT 路径的「使用点即时读取」达到同样的时序语义。
