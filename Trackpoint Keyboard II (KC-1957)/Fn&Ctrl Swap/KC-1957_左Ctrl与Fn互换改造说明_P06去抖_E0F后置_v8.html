KC-1957（nRF52832）左 Ctrl 与 Fn 完全互换改造说明
v8 —— E0F 读取点后置

补丁脚本 fn_swap_debounce_inline_patch.py　·　独立验证脚本 verify_v8.py　·　补丁产物 KC-1957_88_v8.bin（270 字节 / 18 区域）

本版 = v7 + 2.4G 路径 E0F 读取点后置。在 v7「左 Ctrl 与 Fn 完全互换 + P0.6 去抖」的基础上，把 2.4G 扫描路径里「在行循环之前一次性读入 E0F」的结构，改为「在行循环之内每个 row 刷新 E0F」，从而消除 v7 中 2.4G 路径最多滞后 1 个扫描周期的固有现象，与 BT 路径对齐。

v8 直接对原始固件打补丁（KC-1957_88_orig.bin），不依赖 v5/v6/v7 的任何中间产物；BT 路径零字节改动。

型号说明：产品型号是 KC-1957；固件文件名中的 _88_ 是 88 布局代号，与型号无关。MCU 为 nRF52832。

1.1　用户可见的键位行为（与 v6/v7 完全一致，v8 不改变任何键位语义）

1.2　v8 改变的（唯一的）行为差异

1.3　关键设计：只动 2.4G 的两个 trampoline

  1. Trampoline C（0x50200 区）：删掉 v7 里的「读 E0F → mov r7,r0」两步（即把 E0F 装进 r7 的那一步），只保留 P0.6 → 伪 Left Ctrl 注入（读去抖变量 E0F2）。→ 由 40 字节缩到 28 字节。
  2. Trampoline B（0x50100 区）：在 .restore 处新增「ldr.w r7,[pc] + ldrb r7,[r7]」两步，即每个 row 都把当前 E0F 重新读进 r7。→ 由 64 字节增到 72 字节。

净变化 −4 字节（v7 = 274 字节 / 18 区域 → v8 = 270 字节 / 18 区域）。

二、改造背景：v7 遗留的结构性滞后

2.1　v7 的 2.4G 路径结构

v6 把 2.4G 的 Fn 判定源从 GPIO P0.6 换成矩阵 r15c0 之后，2.4G 扫描函数里就形成了这样一段结构（这是 v6 引入的，v7 未改变）：

2.4G 扫描函数 FUN_00041180
  │
  ├─ HOOK_C @0x411C6 ── 一次性把 E0F 读进 r7
  │      （trampoline C 的第一段：ldr.w r0,[pc] / ldrb r0,[r0] / mov r7,r0）
  │      ※ 此刻 E0F 还是【上一轮扫描】留下的值
  │
  └─< 行循环 r4 = 0 .. 15 >
         ├─ HOOK_B @0x41252 ── 扫描到 row15 时写 E0F = 本轮结果
         ├─ 内层列循环 0x41268 .. 0x4131A
         ├─ 0x41286  cbz r7   ← 消费点 ①（行循环内）
         └─ ...
     └─ 0x413D0  cbz r7   ← 消费点 ②（行循环后）
问题：r7 在行循环之前就被冻结成了上一轮的快照，而循环内、循环后两处 cbz r7 全程都读这个快照。行循环后那个消费点 0x413D0（Fn 后置动作）本应反映「本轮刚扫完」的结果，实际拿到的是上一轮。

2.2　BT 路径为什么没有这个问题

BT 路径的 E0F 读取点在 HOOK_D（0x1EB74），位于 BT 扫描流程内部，紧邻其消费点；且 E0F 的写入点 HOOK_A（0x1E4E4）地址在前、读取点 HOOK_D（0x1EB74）在后，同处一次扫描流程内。

图 1：BT 路径的 E0F 写入点与读取点在同一次扫描流程内且写在前 → 结构上无滞后。

2.3　影响面评估

滞后对象是修饰键状态位（Fn 标志），不是键码本身：Fn 本身不产生独立键码（KEYTBL[120] = 0x00），它只决定 Fn 层（0x20002109 = E0F && D7B）是否激活、以及 Fn 修饰位是否出现在 HID 报告里。

  1. Fn 后置动作（0x413D0）比 Fn 按下晚一拍——例如「Fn + 某键」组合中，Fn 层的展开/收起比按键本身晚一个扫描周期；
  2. 松手时多残留一拍——Fn 刚松开时，行循环后的后置动作仍会按「Fn 还按着」执行一次。

v8 把这个残留窗口消除，同时不引入任何新的时序风险（见第十章）。

cbz r7 ≡ 「Fn（P0.6）未按下」分支（r7 的取值只可能是 0 或 1）。

v6 起把 r7 的载体从 P0.6 换成矩阵 Fn（E0F），分支极性保持一致：

原始固件： r7 = (P0.6 按下) ? 1 : 0     →  cbz r7 = 「P0.6 未按下」
v6 / v7：  r7 = E0F（矩阵 Fn 标志）      →  cbz r7 = 「矩阵 Fn 未按下」（E0F == 0）
v8：       r7 = E0F，每 row 刷新          →  cbz r7 = 「矩阵 Fn 未按下」（本轮最新 E0F）

v8 的改动只发生在「r7 何时被重新赋值」这一项上，不改变 r7 的语义、不改变分支极性：

安全性推论：0x4119C（W3）位于行循环之前、0x413AE（W5）位于行循环之后，两者都不影响两个消费点；而行循环内 trampoline B 在 0x41252 执行、早于 0x41286，因此即使删掉 HOOK_C 的赋值，r7 在两个消费点处也始终是已定义且新鲜的。

三个关键事实：
  1. r7 在 2.4G 扫描函数内被两处 cbz 消费：0x41286（行循环内）与 0x413D0（行循环后）。这是 v8 设计的全部依据——补丁脚本把这两条 cbz r7 的存在写成了启动时断言。
  2. 外层行循环 r4 从 0 递增到 0xF，row15 是最后一行。矩阵式 Fn（r15c0）的 E0F 只在最后一次迭代才被最终确定。
  3. HOOK_B 位于行循环内、且在 0x41286 之前执行——这正是 v8 刷新 r7 的落点。

4.3　为什么「行循环内刷新」就能消除滞后

关键在于 row15 是外层行循环的最后一次迭代：

  • 迭代 r4 = 15 时，HOOK_B 先把 E0F 写成本轮结果，紧接着在 .restore 处执行 r7 = E0F；
  • 之后外层循环 r4 递增到 0x10，blo.w 不再跳转，退出行循环；
  • 循环后的 0x413D0 cbz r7 读到的 r7 就是本轮 row15 刚写下的值 → 与 BT 的「同一轮内写完再读」完全对称。
固有 1 周期说明：矩阵式 Fn（r15c0）的 E0F 必须在扫描到 row15 时才最终确定，而 row15 排在最后一行，因此相对「GPIO 直读式 Fn（P0.6）零滞后」必然存在最多 1 个扫描周期的固有滞后。v8 消除的是「用上一轮的值」这个额外的一拍，使 2.4G 与 BT 的行为完全一致。

  • 唯一落在「行循环之前、且会影响消费点」的写入，就是 v7 trampoline C 的 mov r7,r0；
  • v8 删掉它，改由 trampoline B 在行循环内每 row 执行一次 r7 = E0F，且 trampoline B 位于 0x41252、早于 0x41286。
因此两个消费点处的 r7 在 v8 中始终是已定义且新鲜的（本轮 E0F），不会产生未定义行为。

十、已知限制与风险

10.0　两条使用前提（务必先看）

① 硬件版本：必须使用 V2 及以上硬件 Dump 出来的固件。 本补丁的注入地址、行掩码位、键位表偏移全部基于 V2+ 硬件的固件布局逆向得出。V1 等低版本硬件的固件布局不同，这些地址与假设不成立，强行打补丁会得到行为不可预期甚至变砖的固件。
  • 若你的设备是低版本：本补丁不适用，不要尝试；需自行向持有 V2+ 设备固件的人索取一份 V2+ 固件（512 KB 主 Flash 文件）再打补丁。
  • 如何确认：直接对 Dump 出来的固件干跑补丁脚本（python fn_swap_debounce_inline_patch.py <固件>）。干跑会检查键位表特征、ROWPIN 表、行掩码位、钩子代码点、代码空洞是否全 0xFF、新变量选址窗口是否冲突等。V2+ 固件会顺利通过全部检查；V1 固件会在某一项上明确中止并说明原因。 干跑不写盘，对固件无任何影响。
② 不要用 SHA-256 判断固件或补丁对不对。 每台设备 Dump 出来的固件本来就不完全一样 —— 512 KB 主 Flash 中含设备独有内容（蓝牙名称 @0x21228、2.4G 无线 ID @0x78054）。因此原厂固件与补丁产物的 SHA-256 都因机而异。

实测：在两台设备上跑同一套补丁，两个补丁产物之间仅 18 字节不同，且全部落在上述设备独有数据区 —— 即改造逻辑在任意设备上逐字节一致，变的只有设备自己的身份数据。

唯一可靠的判据是本脚本的结构性检查（见 9.1 第 2/3 项：差异区间精确等于预期 18 段、其余 524018 字节逐字节未变）与补丁脚本的前置检查。verify_v8.py 打印的哈希仅作参考，不参与通过判定。

10.1　矩阵式 Fn 的固有 1 周期（无法消除，也不需要消除）

矩阵 r15c0 的 E0F 必须等到 row15 才最终确定，而 row15 是最后一行。因此相对「GPIO 直读式 P0.6 零滞后」，矩阵 Fn 天然存在最多 1 个扫描周期的滞后。v8 消除的是额外的那一拍（2.4G 用上一轮的值），而不是这一拍。

若要求 P0.6 与矩阵 Fn 完全同拍，只能把 Fn 改为 GPIO 直读（放弃 SL410K 盘体适配）——与 v5 的改造动因冲突，故不做。

10.2　2.4G 路径行循环内的 Fn 次级行为仍可能用上一轮值

0x41286 cbz r7（行循环内）位于列循环之中，r4 ∈ 0..14 时 row15 尚未扫到，E0F 还是上一轮的值。这是矩阵式 Fn 的固有性质，BT 路径同样如此（同一份矩阵数据、同样的 row15 依赖）。v8 做到的是让两条路径行为一致，而不是让行循环内也变成零滞后。

10.3　实机验证建议

v8 相对 v7 只改变「2.4G 通道 Fn 状态的取样时刻」，不改变任何键码输出。

十一、踩坑与逐步确认（正确性保障）

11.1　v8 排障：keystone 初始化报 KS_ERR_ARCH

现象：补丁脚本启动即 keystone.keystone.KsError: Invalid/unsupported architecture (KS_ERR_ARCH)。

根因：脚本写成 Ks(CS_ARCH_ARM, KS_MODE_THUMB)——CS_ARCH_ARM 是 capstone 的常量（值 0），而 keystone 里 0 是 KS_ARCH_INVALID，KS_ARCH_ARM 的值是 1。两个库的架构枚举不是同一套编号；CS_MODE_THUMB 与 KS_MODE_THUMB 恰好都是 16，所以 mode 参数没暴露问题、只有 arch 参数出错。

修复：ks = Ks(KS_ARCH_ARM, KS_MODE_THUMB)（用 keystone 自己导入的常量）。一行。

教训：跨库调用时不能凭名字相似就混用常量。capstone.CS_ARCH_ARM == 0、keystone.KS_ARCH_ARM == 1，CS_MODE_THUMB == KS_MODE_THUMB == 16。

11.2　验证脚本解析 capstone 反汇编的两个坑

  1. mnemonic 带 .w 后缀：ldr.w / tst.w / ldrb.w 的 mnemonic 字段分别是 'ldr.w'、'tst.w'、'ldrb.w'，与 'ldr'、'tst' 不相等。比较前必须先 .replace('.w', '')，否则所有基于 mnemonic 的判定会静默失效（表现为「提取不到 row/bit」「找不到 E0F 字面量」）。
  2. 字面量池会被继续反汇编成伪指令：trampoline 尾部的池数据（如 0F 1E 00 20）会被 capstone 解释成 subs r7,r1,#0 / movs r0,#0 这样的“指令”。判定「代码区末尾」必须以 bx lr 为界截断，不能用「blob 总长度」当代码区长度（v8 trampoline B 总长 72 字节、代码区只有 60 字节）。

11.3　为什么必须刷新「行循环内」而不是「行循环后」

一个自然的想法是「把 E0F 读取点直接放到 0x413D0 之前」。但那样只解决消费点②，消费点①（0x41286，行循环内）就会读到未定义/陈旧的 r7——因为 r7 在 2.4G 函数内没有其他写入点。

v8 的选择是在行循环内逐 row 刷新 r7（trampoline B 的 .restore），一举两得：

  • 消费点①（0x41286）：r4 = 15 那次迭代拿到本轮值，其余行仍是上一轮（与 BT 同构，矩阵固有限制）；
  • 消费点②（0x413D0）：循环退出时 r7 是 row15 那次迭代刷新的值 = 本轮最新。

11.4　为什么删除 HOOK_C 的 r7 赋值是安全的

依据（见 §3.3.1 的完整枚举）：r7 在 2.4G 扫描函数体内的 3 处写入分别是 0x4119C（序言 mov r7,fp ⇒ 初值 0）、0x411CE（HOOK_C 的 movs r7,#1）、0x413AE（尾声 pop 恢复）；2 处消费是 0x41286 与 0x413D0 两处 cbz r7。

其中序言那次在行循环之前、尾声那次在行循环之后，唯一会影响消费点的前置写入就是 v7 trampoline C 的 mov r7,r0。删除它、并把该写入挪到行循环内的 trampoline B（0x41252，早于 0x41286）之后，r7 在两个消费点处始终有定义且是本轮最新值，不产生任何新的未定义行为。

附带结论：原始固件中 r7 初值为 0（因 mov.w fp,#0），且只有 P0.6 按下时才置 1，故 cbz r7 的原始语义就是「Fn（P0.6）未按下」。v6 把载体换成矩阵 Fn 后语义自然变成「矩阵 Fn 未按下」，v7/v8 只是改变取样时刻，不改变语义与极性。

11.5　逐步确认清单

  • 2.4G 函数体内 r7 的全部写入点与消费点已枚举（1 处写、2 处读）；
  • 0x41286 / 0x413D0 两条 cbz r7 已在成品固件中复核存在；
  • 写入点（HOOK_B，row15 生效）在读取点（trampoline B .restore）之前，且在同一 row 迭代内；
  • row15 是外层行循环的最后一次迭代（0x413BE cmp r4,#0x10 / 0x413C0 blo.w）；
  • BT 路径的写入点 0x1E4E4 < 读取点 0x1EB74，同处一次扫描流程，无需改动；
  • trampoline B 的 .restore 精确复原原指令 ldrb.w r2,[sl,r4] 与标志位 cmp r0,#0；
  • 全部 5 个 trampoline 落点在写入前为空洞（0xFF），无越界；
  • 固件长度不变（524288），向量表 Reset_Handler 不变。
