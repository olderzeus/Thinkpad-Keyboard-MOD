KC-1957（nRF52832）左 Ctrl 与 Fn 完全互换改造说明

补丁脚本 fn_swap_patch.py（v6）　独立验证脚本 verify_v6.py　补丁产物 KC-1957_88_v6.bin（274 字节 / 18 区域）

本版直接在原始固件（KC-1957_88_orig.bin）上打补丁，不依赖 v5 或任何中间版本。所有 ASM 行均附真实二进制数值（取自最终固件，与补丁脚本逐字节一致）。

改造背景：左 Ctrl 与 Fn 完全互换，是为满足部分用户对键位布局的使用习惯需求——将最左下角原本的 Left Ctrl 改为充当 Fn，同时将 Fn 所释放出的位置（矩阵 r12c4 与 GPIO P0.6）改为发 Left Ctrl，使习惯该布局的用户无需改变肌肉记忆即可使用。

一、最终结果和逻辑

一句话结论：把 Fn 的判定源从「P0.6 GPIO」整体换成「矩阵 r15c0」，同时把 键位映射对调——r12c4 与 P0.6 发 Left Ctrl，r15c0 当 Fn 用。

改造后固件里 P0.6 完全不再参与 Fn 语义：2109 = E0F && D7B（Fn 层激活）中的 E0F 已变成「矩阵 r15c0 按下」，而 P0.6 只剩下「发 Left Ctrl」这一条作用。

物理位置改造前行为改造后行为实现方式
矩阵 r12c4（idx 100，原空槽）空槽，不产生任何键码发 Left Ctrl（0xE0）键码表改为 0xE0 + 行掩码放行 bit4
GPIO P0.6（旧 Fn 键，低有效）Fn（激活 Fn 层）发 Left Ctrl（0xE0）BT 侧在 HID 组装处注入修饰位；2.4G 侧把伪键 0xDF 改成 0xE0

1.1　关键设计：只改一个字面量池槽

固件里 Fn 状态变量 E0F @ 0x20001E0F 被 20 处 引用，分布在 6 个 Thumb 字面量池槽里：

池槽引用数所属函数语义v6 处理
0x1B8A06（2 写 4 读）FUN_0001b75c P0.6 去抖状态机独占写 E0F改指 E0F2（新变量）

0x1ECD02（读）FUN_0001e40c 蓝牙扫描读 E0F不动 → 自动跟随矩阵 Fn

0x020FD42（读）FUN_00020bd8 计算 2109读 E0F不动 → 自动跟随矩阵 Fn

于是：

  • 唯一写入 E0F 的去抖状态机被「隔离」到新变量 E0F2，P0.6 的去抖照常进行，但不再污染 E0F；
  • 14 处读取 E0F 的代码一行都不用改，全部自动改为跟随矩阵 Fn；
  • 其中最关键的 FUN_00020bd8：if ((E0F == 1) && (D7B == 1)) { *2109 = 1; } 变成 2109 = 矩阵Fn && D7B —— P0.6 不再激活 Fn 层。

反向的「Fn → Left Ctrl」完全走既有通路，不新增任何代码：

键码表里的 0xE0 由两条扫描路径分别交给各自的 HID 组装函数，按 1 << (code - 0xE0) 转成修饰位 0。

2.4G 路径（直接）：键码表 0x4A6FA[120] 本来就是 0xE0，扫描后进入键码数组，由 2.4G 报告组装按 0xE0 → 修饰位 0 处理。这条通路由原始固件自证。

蓝牙路径（三表串联 + 位图双保险）：BT 扫描遇到 0xE0–0xE7 → 写入修饰键表 0x20002E81 → 并入扫描键码数组 0x20002E61 → 写入上报候选表 0x20002E94（= param_1）；另有 DAT_0001f1c4 |= 1 << (code-0xE0) 独立维护修饰位图。HID 组装 FUN_00023a40 遍历候选表，遇 [0xE0,0xE7] → *param_1 |= 1 << (code-0xE0)。两条都不需要本补丁新增代码——本补丁只需把 KEYTBL_BT[100] 由 0x00 改成 0xE0，即接入既有通路。

2.3　修饰位从键码到 HID 报告的完整通路（复核补记）

「把某个键位变成 Left Ctrl」不是靠键码表一个字节就够的 —— 必须确认 0xE0 这个码值确实会被固件翻译成 HID 报告里的修饰字节位 0。逐字节追踪的结果如下（BT 与 2.4G 各一套）：

环节蓝牙（BT）2.4G
① 键位产生码值KEYTBL_BT[100] → 0xE0KEYTBL_G[100] → 0xE0
② 扫描阶段归类命中 0xE0–0xE7 → 写入修饰键表 0x20002E81写入键码数组
③ 并入上报候选0x20002E61[] → 0x20002E94（param_1）直接在数组内
④ 修饰位图（独立通路）DAT_0001f1c4 |= 1<<(code-0xE0)无（2.4G 另有右修饰位图）
⑤ HID 组装FUN_00023a40：[0xE0,0xE7] → *param_1 |= 1<<(code-0xE0)2.4G 报告组装：0xE0 → 修饰位 0

关键结论：第 ⑤ 步的 1 << (code - 0xE0) 转译在两条路径上都存在，所以「键码表里放 0xE0」这个做法是固件原生的、无需新增代码的通路。本补丁把 KEYTBL_BT[100] / KEYTBL_G[100] 由 0x00 改成 0xE0，即等于接入了这条既有通路。

复核补记：早期版本曾把这条通路概括成「键码表里的 0xE0 原样交给 HID 组装函数」，并以 KEYTBL_G[120] 原本就是 0xE0 作为「已被原始固件自证」的依据。该依据只对 2.4G 成立——蓝牙侧的实际链路是上表的三表串联 + 位图双保险。结论（r12c4 可作 Left Ctrl）不变，但依据已按上表更正。

  • 注入点安全性（复核补记）：0x23A78 之后，*param_1（修饰字节）在 0x23A7A–0x23AF0 区间内只有一处写操作 —— 0x23AE4: strb r3,[r1]，且其前一条 0x23AE2: orrs r3, r5 是 OR 累加而非赋值。因此 HOOK_E 注入的 bit0 不会被后续逻辑清掉或整体覆盖。（容易误认的是 0x23A64: strb r3,[r4] —— 它写的其实是 0x20002107 这个另一个变量，不是 *param_1。）

八、已知限制与风险

  1. P0.6 的去抖在 v6 中不再用于 Ctrl 注入。

由于 E0F 被整体换源，FUN_00020bd8 里「P0.6 松开 && E0F==1」的边沿判定随之失效，P0.6 的去抖状态机（写入 E0F2）不再被可靠地「武装」。因此 Ctrl 注入统一采用原始 P0.IN bit6——这与原固件在 2.4G 路径（HOOK_C）和蓝牙扫描内联处（HOOK_D 改造前）对 P0.6 的用法一致。代价：P0.6 的电气抖动理论上会造成极短暂的 Ctrl 按下/抬起。若实机发现抖动明显，可改为读 E0F2（但需同时修好 FUN_00020bd8 的边沿判定，见下文「可选加固」）。

  1. 2.4G 路径的 Fn 门控已整体换成矩阵 Fn（复核更正）。

2.4G 扫描函数用寄存器 r7 作为 Fn 门控：0x41286: cbz r7, #0x412ca（r7 == 0 → 跳过 Fn 映射分支）与 0x413D0: cbz r7, #0x41422（同类）。原固件里 r7 仅由 0x411CE: movs r7,#1（P0.6 按下）置位，本改造把该来源换成 E0F（矩阵 r15c0）。r7 在 0x41526 / 0x416A4 之后被复用为循环变量，与 0x411C6 的写入点不冲突，替换是安全的。

  1. 蓝牙与 2.4G 两条路径共用 E0F。

正常情况下同一时刻只有一条协议在跑，扫描函数不会互相覆盖；若固件存在两种协议同时扫描的路径，需要把 E0F 拆成两个变量。

  1. 无实机验证条件。

本次改造的全部结论来自静态分析 + 反汇编复核 + 行为仿真，没有实机刷写验证。请在有回滚手段（.bak 备份 / 原始固件）的前提下上机测试。

  1. Fn 层键码表未被改动 —— r12c4 的 Left Ctrl 只在「非 Fn 层」生效（复核补记）。

固件的 Fn 层键码表在 0x2CC78（128 字节，按 idx = row*8+col 索引，池槽 0x020B48 指向它），本补丁只改了主表 0x2CBF0 / 0x4A6FA，没有动 Fn 层表。该表 idx100 (r12c4) = 0x1C、idx120 (r15c0) = 0xC1 保持原样。影响：按住 Fn（现在 = r15c0）时再按 r12c4，走的是 Fn 层重映射（0x1C），不是 Left Ctrl；只有不按 Fn 时 r12c4 才是 Left Ctrl。这与原固件的行为差异为零（原固件 r12c4 本身就是空槽，Fn 层同样给 0x1C），但使用时应注意：Left Ctrl 与 Fn 不可同时使用。

可选加固（若实机发现 P0.6 抖动）

让 FUN_00020bd8 的「P0.6 松开 && E0F==1」判定改读 E0F2，即可让 P0.6 的去抖重新可靠工作，随后把两处 Ctrl 注入改为读 E0F2：

  • 0x020FD4 池槽：0x20001E0F → 0x20004800（E0F2）；
  • 但这样 2109 = E0F && D7B 就会用 E0F2（P0.6）计算，P0.6 又会变回 Fn，因此还需要把 FUN_00020bd8 中 0x20C0C 那条 ldr r0,[pc,#0x3C4] 改指到另一个装 0x20001E0F 的池槽（该函数字面量池 0x20FC0-0x20FCC 有 4 个 0 引用槽可利用）。

9.2　逐步确认的关键点

  1. 关键常量必须取自原始固件实测：ROWPIN(0x2CBE0)、E0F(0x20001E0F)、P0.IN(0x50000510) 的目标地址，均通过读取原指令的 pc 相对字面量池逐一核对，而非凭记忆。所有 ASM 行的二进制数值均由本说明配套的提取脚本从 KC-1957_88_v6.bin 逐字节读出。
  2. 寄存器契约核对：BT 调用点 r0=local_64[r5]、2.4G 调用点 r0=local_84[r4]，均在 bl 之前成立（重算 r0 发生在调用点之后），故 trampoline 内 tst r0,#1 检测的就是 r15c0；返回前精确复原被覆盖的 r1（BT）或 r2（2.4G）。
  3. RAM 选址安全：按函数边界精确普查 2434 个函数实测，全映像 pc 相对字面量引用的 RAM 变量共 661 个，最高只到 0x20003928，其上零引用；E0F2@0x20004800 取最高引用 +3616 字节，既避开数组延伸风险，又距 RAM 顶端仍有约 28KB。补丁脚本启动时会现场复核 0x20004800-0x20004900 窗口内引用数为 0。
  4. 并行路径隔离：BT 子树与 2.4G 子树零交集；2109/D7B 为 BT 专属，2.4G 用自身标志 r7 驱动，互不干扰。
  5. 新变量唯一性：二进制扫描确认 trampoline 区常量集仅含 E0F / E0F2 / P0.IN / ROWPIN，绝不出现 0x20002109 / 0x20001D7B / 0x20001E09。

而v5.1 的两处关键修正字节，v6 原样继承、一字未改——这正是 v6 不必再单独踩坑的原因：

偏移v5.1 与 v6 完全相同的字节作用
0x5011220 F0 xx 00bic r0, r0, #N —— 清理寄存器 r0（2.4G 路径钩子之后的逐位测试用的就是 r0，不是数组）
0x5013200 28cmp r0, #0 —— 复原 0x4125E 的 beq 所依赖的 Z 位（源自 0x4124C 的 bics）

沿革小结：v5 原始版只清 local_84[r4]、且未复原 Z 位（→ 2.4G 路径根本没屏蔽住目标键、且第 12 行其它按键可能被整行丢弃）→ v5.1 用上表两条指令修好 → v6 直接沿用修好后的结构，只把行号（12→15）、检测位（bit4→bit0）、写入目标（FN_MATRIX→E0F）换成本版语义。

11.2　Trampoline A / C / D：属语义替换，非缺陷修正

Trampolinev5.1（Fn 矩阵化）v6（Ctrl/Fn 互换）差异字节
A @0x50000（60 B）写 FN_MATRIX=1 + 强制 E0F=1（与 P0.6 并联）+ 清 local_64[12] bit4写 E0F=1（整体换源）+ 清 local_64[15] bit043 / 60
C @0x50200（40 B）Fn 判定 OR：P0.6 低 或 FN_MATRIX → 写伪键 0xDFr7 = E0F（矩阵 Fn 作 2.4G 门控）+ P0.6 低 → 写伪键 0xE024 / 40
D @0x50300（24 B）保护 E0F 的去抖清除不被 FN_MATRIX 路径打断蓝牙扫描内联读：P0.IN bit6 → 改读 E0F19 / 24
E @0x50400（28 B）—（该区在 v5.1 中为擦除态 0xFF）BT HID 组装处注入 Left Ctrl 修饰位28 / 28（v6 新增）

需要强调的是：C / D 的改动不是「修 bug」，而是「换语义」——v6 的 Fn 判定源整体从 P0.6 迁到矩阵 r15c0，这两条路径的取值来源必须随之改变。

11.3　v6 新增①：补丁脚本的启动时自检

v5 的补丁脚本没有启动自检；v6 新增两项，任一不满足即直接中止，而不是打出一个静默失效的固件：

自检项检查内容不满足时的后果
ROWPIN 池槽一致性HOOK_A 覆盖掉的那条 ldr r1,[pc,#imm]，其字面量池槽 0x1E858 的值必须 == ROWPIN(0x2CBE0)中止：否则 trampoline 还原的 r1 与原始指令不等价，后续 ldrb r2,[r1,r5] 会读到错误地址
row15 的 bit0 放行蓝牙行掩码 row15 的 bit0 必须为 1（高有效放行 col0）、2.4G 行掩码 row15 的 bit0 必须为 0（低有效放行 col0）中止并提示「Fn 将永不触发」

11.4　v6 新增②：G 组「改造前提交叉验证」

验证脚本新增 G 组 10 项，全部是对改造前固件的前提性交叉验证——即「如果这些前提不成立，补丁就不该被认为正确」：

  1. 蓝牙 / 2.4G 行掩码 row15 的 bit0 状态（保证 r15c0 参与扫描）；
  2. HOOK_A 覆盖的 ldr 池槽值 == ROWPIN；
  3. *param_1 在 0x23A7A–0x23AF0 内只有 0x23AE4 一处写且为 OR 累加（HOOK_E 注入不被覆盖）；
  4. HOOK_C 之后的 0x411D8 movs r4,#0 完好；
  5. HOOK_D 之后的 0x1EB8A 条件分支完好；
  6. Fn 层键码表 0x2CC78 未被改动。

11.5　改动范围与验证

  • 与 v5.1 相比：改动集中在 Trampoline A / C / D（语义换轨）与新增的 Trampoline E；Trampoline B 仅 8 字节不同（见 11.1）。
  • 与原始固件相比：改动 274 字节 / 18 区域。
  • 验证：verify_v6.py 独立脚本 87 项全部通过；其中 E 组用最小 Thumb 解释器逐条执行 5 个 trampoline 做行为仿真，G 组做 10 项前提交叉验证。
  • 补丁脚本 fn_swap_patch.py 全部自检通过：代码区完整解码、字面量池常量序列、imm12 回填、RAM 选址窗口复核、语义自洽检查、ROWPIN 池槽、row15 bit0 放行。

11.6　顺带更正的一处对 v5 版本的表述

本文档 5.2 节与 9.1 节此前把「2.4G 路径未清 r0 的 bit0、未复原标志位」记在「v5 的 Trampoline B」名下。经与 KC-1957_88_fn7_v51.bin 逐字节核对，准确表述应为：

  • 该缺陷存在于 v5 原始版；
  • v5.1 已修正（v5 文档「v5.1 修订记录」章即记这两件事）；
  • v6 沿用 v5.1 修好后的结构，只把行号、检测位与写入目标换成本版语义（详见 11.1）。

结论不变（v6 的 2.4G 路径两处均正确），仅归属表述更精确。
