KC-1957（nRF52832）Fn 键矩阵化改造说明

最终版（v5.1）· 补丁脚本 fn_matrix_patch3.py（v5.1：支持掩码不符时 --force-mask 强制修补，并修正 2.4G 路径 Trampoline B 的两处缺陷）· 补丁产物 KC-1957_88_fn7_v51.bin（246 字节 / 10 区域）· 所有 ASM 行均附真实二进制数值（取自最终固件，与补丁脚本逐字节一致）。

一、最终结果和逻辑

一句话结论：把 Fn 从“单独的 P0.6 GPIO”扩展为“P0.6 拉低 或 键阵 r12c4 按下”的并联判定；除新增 1 字节锁存 FN_MATRIX@0x20004800 外，不引入任何新内存变量，也不改动任何其它判定逻辑。蓝牙（BT）与 2.4G 两条独立扫描路径均完成改造，二者行为一致、互不影响。

改造背景：本次 Fn 键矩阵化改造源自适配 SL410K 盘体 的需要。SL410K 盘体上 Fn 不再以独立 GPIO（P0.6）形式提供，而须由键盘矩阵承载；本改造把 Fn 扩展为「P0.6 拉低 或 矩阵 r12c4 按下」的并联判定，使 SL410K 盘体在不改动硬件的前提下即可被固件识别，同时保持与原有键盘（仅 P0.6）100% 兼容。

固件原本把 Fn 当作独立引脚 P0.6（低电平有效）识别。改造后，键阵中原本空置的槽位 row12 × col4（固件矩阵坐标：第 12 行第 4 列；col4 即 A/S/D 所在列，第 11–12 行为 Home/End/方向键导航簇）被定义为“虚拟 Fn 键”。当该槽被扫描到时：① 锁存 FN_MATRIX=1；② 清掉该行位图中对应 bit，使该槽不再产生独立键码；③ 通过既有通道把“Fn 按下”上报（BT 走 E0F，2.4G 走伪键码 0xDF）。只要 P0.6 拉低或矩阵 Fn 按下任一成立，即识别为 Fn 被按下，从而保证与原有键盘 100% 兼容。

1.1 键盘矩阵详细结构

固件采用 16 行 × 8 列扫描矩阵，共 128 个键位。MCU 逐行把某行驱动为低电平（行扫描），同时读回 8 条列线，把“被拉低的列”的对应 bit 写进该行的列位图（蓝牙侧 local_64[row]，2.4G 侧 local_84[row]）。键码按 idx = row×8 + col 索引到键码表（row/col 均从 0 起）。

矩阵规模16 行 × 8 列 = 128 键位（键码表 128 项，每项 1 字节）
键码索引idx = row×8 + col。例如 r12c4 = 12×8+4 = 100（0x64）
行引脚表蓝牙 @ 0x2CBE0（16 项，逐行 GPIO 配置）｜2.4G @ 0x4A77A（16 项）
列读取列线经 GPIO 输入回读（蓝牙读 P0 输入端口，2.4G 经 sl 基址的列缓冲）
行循环方向蓝牙 r5 = 15→0（递减）｜2.4G r4 = 0→15（递增）；均需对非目标行跳过，避免误清标志
行扫描掩码蓝牙 @ 0x1E840（高有效，扫描 & mask）｜2.4G @ 0x4A6A6（低有效，扫描 & ~mask）
键码表蓝牙 @ 0x2CC54｜2.4G @ 0x4A75E（各 128 字节）
r12c4 槽两表偏移 0x64 处均为空（0x00），故可安全征用为“虚拟 Fn 键”，且不破坏任何既有键

1.2 Fn 的 GPIO 逻辑

Fn 原有 GPIO 逻辑。Fn 不是矩阵里的键，而是接在 MCU 通用输入引脚 P0.6 上的独立按键，采用低电平有效（active-low）：引脚读为低表示按下、读为高表示松开。固件通过读取 GPIO 输入寄存器 P0.IN @0x50000510 的 bit6 来判定 Fn：(P0.IN & 0x40)==0 即“Fn 按下”。去抖后的值缓存在 E0F @0x20001E0F，扫描函数正是读它来识别 Fn 修饰键。

为什么要把它做成矩阵键。这是适配 SL410K 盘体 的直接需要——SL410K 盘体的 Fn 须由键盘矩阵承载，而非独立 GPIO。把 Fn 也放进键阵（虚拟槽 r12c4）后，既能在不改动硬件的前提下让固件“看见”这个键，又能保持旧键盘（仅 P0.6）照样工作——两条识别路径并联，任一成立即为 Fn。P0.6 拉低 或 矩阵 Fn 按下，均识别为 Fn 被按下，从而保证与原有键盘 100% 兼容。

四、数据补丁（掩码字节）

蓝牙行掩码 @0x1E84C0xE7 → 0xF7　置 bit4，使 r12c4 参与扫描（高有效，扫描时 & mask）
2.4G 行掩码 @0x4A6B20x1C → 0x0C　清 bit4（低有效，扫描时 & ~mask）

两处掩码仅翻转 bit4 一位，键码表 / 重映射表 / 行引脚表均零改动——矩阵 Fn 不产生任何独立键码，仅通过 FN_MATRIX 与既有 Fn 通道联动。

五、掩码不符时的强制修补（v5 新增）

补丁脚本把「原字节安全断言」拆成两类点，以区别对待：

hook 代码点0x1E4E4 / 0x41252 / 0x411C6 / 0x1B7C0　补丁的语义落点，决定改写哪段逻辑硬中止（exit 2）。仅 --force 可放行，且会明示该地址原指令将被完全覆盖、需自行确认落点正确
键盘掩码点0x1E84C / 0x4A6B2　数据字节，仅决定哪些行列参与扫描可用 --force-mask 强制修补：按「实际值 + 位操作」写入，其余位保留变体固件自身的值

5.1 强制修补的关键语义：不套用原版常量

掩码目标值不是写死 0xF7 / 0x0C，而是由实际值按位推出：

蓝牙 0x1E84C
（高有效 & mask）		置 bit4
实际 | 0x10		原版：0xE7 → 0xF7
变体示例：0xE3 → 0xF3（低 3 位保留 E3）
2.4G 0x4A6B2
（低有效 & ~mask）		清 bit4
实际 & ~0x10		原版：0x1C → 0x0C
变体示例：0x10 → 0x00

这样做的意义：变体固件的掩码表若在其它位上与本版本不同，套用原版常量会把那些位一并改错；而按位操作只动 bit4（col4 / ASD 列），其它位原样保留。

5.2 命令行用法

python fn_matrix_patch3.py <in.bin> [--out <out.bin>] [--apply]
                            [--force-mask] [--force]
（无 --apply）干跑：只做全部断言与反汇编复核，不写盘
--apply实际写出补丁固件（自动保留 .bak 备份）
--force-mask键盘掩码与预期值不符时，忽略差异并按位强制修补；hook 代码点仍为硬约束
--force在 --force-mask 基础上，连 hook 代码点的字节差异也一并忽略（该地址原指令将被完全覆盖，风险自担）

5.3 强制修补时的输出提示

掩码不符且未加开关时，脚本先给出预览再中止，便于判断是否该放行：

  !! 键盘掩码与预期值不符（2 处），已中止。
     0x01E84C  期望 E7 实际 E3
     0x04A6B2  期望 1C 实际 10
     若这属于同型号的变体固件（掩码表取值不同、语义相同），
     可加 --force-mask 忽略差异：补丁将按「实际值 + 位操作」强制修补——
       0x01E84C  实际 0xE3 -> 强制写入 0xF3（置 bit4，其余位保留）
       0x04A6B2  实际 0x10 -> 强制写入 0x00（清 bit4，其余位保留）
     不会套用原版常量，因此变体固件掩码表的其余位不会被覆盖。

六、踩坑与逐步确认（正确性保障）

6.1 历次版本的关键错误（均已规避）

v1 / v2把矩阵 Fn 写入了 0x20001D7B——那是主机 HID 报告(0xAA/0xBB)下发的“Fn 档位/模式”标志，会被 FUN_00022e38 覆盖，语义也不是“按下”。本版已弃用该地址。
v3trampoline A 在“松开”分支写 E0F = P0.IN bit6，覆盖掉 FUN_0001b75c 维护的去抖值，使 P0.6 丧失去抖；又写 2109 = *E0F，丢掉原式里的 && D7B 档位门控。本版改为：仅“按下”时强制 E0F=1，松开只撤 FN_MATRIX。
键码表占用早期方案曾把 r12c4 槽写成 0x8C 再用伪键码覆盖，会污染键码表。本版改为直接清行位图 bit4，键码表保持为空。
空洞违规曾误用 0x077xxx 区间。本版按要求全部收回 0x50000–0x60000。
过期构建污染磁盘上曾有一份写入键码表、使用旧空洞的“fn7.bin”。已反推重建真正原始固件（6/6 原始点匹配），重新生成最终 fn7.bin。

6.2 逐步确认的关键点

  1. 关键常量必须取自原始固件实测：ROWPIN(0x2CBE0)、E0F(0x20001E0F)、P0.IN(0x50000510) 的目标地址，均通过读取原指令的 pc 相对字面量池逐一核对，而非凭记忆。
  2. 寄存器契约核对：BT 调用点 r0=local_64[r5]、2.4G 调用点 r0=local_84[r4]，均在 bl 之前成立（重算 r0 发生在调用点之后），故 trampoline 内 tst r0,#0x10 检测的就是 r12c4；返回前精确复原被覆盖的 r1。
  3. RAM 选址安全：按函数边界精确普查 2434 个函数实测，全映像 pc 相对字面量引用的 RAM 变量共 661 个，最高只到 0x20003928，其上零引用；FN_MATRIX@0x20004800 取最高引用 +3616 字节，既避开数组延伸风险，又距 RAM 顶端仍有约 28KB。（早期版本写的「最高到 0x20004138（654 个地址）」是宽松扫描把落在指令中间的半字误当成 ldr 造成的误报，已按精确普查更正；补丁脚本启动时会现场复核 0x20004800-0x20004900 窗口内引用数为 0。）
  4. 并行路径隔离：BT 子树（48 函数）与 2.4G 子树（10 函数）零交集；2109/D7B 为 BT 专属，2.4G 用自身标志 0x200001C8 bit0 驱动，互不干扰。
  5. 新变量唯一性：二进制扫描确认 trampoline 区常量集仅含 FN_MATRIX / E0F / P0.IN / ROWPIN，绝不出现 0x20002109 / 0x20001D7B / 0x20001E09。

6.3 最终独立复核（_verify_v4.py + _test_v5.py）

对 KC-1957_88_orig.bin ↔ KC-1957_88_fn7_v51.bin 逐项断言，全部通过：

  • 改动 246 字节 / 10 区域，无越界；
  • 两处掩码仅翻转 bit4；键码表 / 重映射表 / 行引脚表零改动；
  • 向量表 Reset_Handler 不变（仍为 0x00000A81）；
  • trampoline 区常量集仅 FN_MATRIX / E0F / P0.IN / ROWPIN，未引入 2109 等其它变量。

另由 _test_v5.py 覆盖 4 条执行路径（正常 / 掩码强制 / 代码点强制 / 两者皆不符），33 项断言全部通过。

结论：补丁严格限定为“Fn 判定 = P0.6 拉低 或 矩阵 r12c4 按下”的并联，除 FN_MATRIX 外未引入任何新内存变量，也未触动其它判定逻辑。

十一、v5.1 修订记录

背景：做 v6（左 Ctrl 与 Fn 完全互换）改造时，需要把 v5 的 Fn 矩阵化机制逐条拆开重新验证，顺带把两条扫描路径的行循环全部读了一遍 —— 结果发现 v5 的 Trampoline B（2.4G 行循环）有两处实质缺陷。这两处都是 v5 自身的推理盲区，直到 v6 逐指令核对 2.4G 路径才暴露出来。

11.1 缺陷 1：2.4G 路径根本没有屏蔽住 r12c4

v5 的做法：Trampoline B 里清 local_84[r4] 的 bit4。

为什么无效：2.4G 扫描函数在钩子之后是这样逐位测试的：

0x04124C   90 43  bics    r0, r2              
0x04124E   41 F8 24 20  str.w   r0, [r1, r4, lsl #2]; local_84[r4] = r0
0x041252   1A F8 04 20  ldrb.w r2, [sl, r4]      
0x041256   08 FA 02 F1  lsl.w   r1, r8, r2        
0x04125A   D5 4A  ldr     r2, [pc, #0x354]  
0x04125C   11 60  str     r1, [r2]          
0x04125E   6E D0  beq     #0x4133e          
0x04126C   10 EA 0C 0F  tst.w   r0, ip

被测对象是寄存器 r0，不是 local_84[r4]。v5 只改了数组里的那一份，寄存器 r0 里的 bit4 还在，于是 tst.w r0, ip 依然会命中 r12c4 那一列。

对比蓝牙路径：BT 的逐位测试读的是数组 ——

0x01E678   07 A8  add     r0, sp, #0x1c     
0x01E67A   50 F8 25 00  ldr.w   r0, [r0, r5, lsl #2]; r0 = local_64[r5]

所以 v5 在 BT 侧清 local_64[r5] 是对的。两条路径的行为不对称，根源就在这里 —— v5 当时按 BT 的模型去写 2.4G 的 trampoline，就写错了。

实际后果：2.4G 模式下 r12c4 虽然查表得到 0x00（不会发出假键码），但它仍被当成「有键按下」，影响该行的按键计数与 local_40 / local_34 / local_2c 分类逻辑。

v5.1 的修法：Trampoline B 里同时清寄存器 r0 与 local_84[r4] 的 bit4。

11.2 缺陷 2：第 12 行的其它按键被整行丢弃

v5 的 Trampoline B 里有 cmp r4,#12 / tst.w r0,#0x10 / movs r2,#0|1，它们都会改写 NZCV；而钩子返回后 0x4125E 的 beq #0x4133E 依赖的正是 0x4124C bics 产生的 Z 位（中间夹着的 ldr / lsl.w / str 都不改标志）。于是：

场景原始 bics 的 Zv5 返回时的 Zbeq 结果后果
r4 ≠ 12行空则 1 / 非空则 0cmp r4,#12 → 0不跳正常（恰好蒙对）
r4 = 12，r12c4 按下0movs r2,#1 → 0不跳正常
r4 = 12，r12c4 未按、该行有其它键0movs r2,#0 → 1跳整行 r12 的其它键全部丢失
r4 = 12，整行为空1movs r2,#0 → 1跳正常

v5.1 的修法：返回前用 cmp r0,#0 复原标志位。r0 此刻已经是「屏蔽掉 r12c4 之后」的位图，Z =（该行是否还有别的键），与原 bics 的语义完全一致 —— 特别地，当该行只剩 r12c4 时 Z=1 → 跳过该行，这正好等价于原固件「r12c4 被掩码、该行本就是空」的行为。

11.5 顺带更正的一处文档错误

v5 原文档与脚本注释都写「全映像真实引用 RAM 变量最高到 0x20004138（654 个地址）」。按函数边界精确普查（2434 个函数逐个反汇编）实测为 661 个地址、最高 0x20003928，0x20004138 实为 0 处引用 —— 它是宽松扫描（每 2 字节扫一次）把落在指令中间的半字误当成 ldr 造成的误报。

选址结论本身不受影响：FN_MATRIX@0x20004800 距真实最高引用仍有余量 3616 字节，距 RAM 顶端约 28KB。v5.1 已在脚本注释、运行输出与本文档中全部更正，并给脚本加了启动时的窗口复核（0x20004800-0x20004900 内引用数必须为 0）。
