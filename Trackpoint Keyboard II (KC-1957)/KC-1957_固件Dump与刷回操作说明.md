# KC-1957 主板固件 Dump 与刷回操作说明

> 适用对象：KC-1957 主板（MCU 为 nRF52832；部分早期资料中也称为「WK-8855 控制板」，二者为同一硬件）。
> 工具链：SEGGER **J-Link OB** + **J-Flash**（通过 SWD 接口读写 nRF52832 内部 Flash）。
> 目的：完整备份主板原始固件（Dump），以及在需要时把备份（或已修改的）固件刷回主板。
>
> **⚠️ 核心原则：刷回固件前，必须「先抹除 → 再写入 → 最后校验」，三步缺一不可。**

---

## 0. 两条重要前提

### 0.1 固件版本：必须使用 V2 及以上硬件的固件

本仓库提供的改造补丁，其注入地址、行掩码位与键位表偏移全部基于 **V2+ 硬件**的固件布局逆向得出。

- **V1 等低版本硬件的固件布局不同**，这些地址与假设不成立，强行打补丁会得到行为不可预期甚至变砖的固件。
- **若你的设备是低版本**：本仓库的补丁不适用，请不要尝试；需要**自行向持有 V2+ 设备固件的人索取**一份 V2+ 固件（512 KB 主 Flash 文件）再打补丁。
- **如何确认自己的固件是否适用**：直接对 Dump 出来的固件**干跑**补丁脚本 ——

  ```bash
  python fn_swap_debounce_inline_patch.py KC-1957_88_orig.bin
  ```

  补丁脚本在写盘前会检查键位表特征、ROWPIN 表、行掩码位、钩子代码点、代码空洞是否全 `0xFF`、新变量选址窗口是否冲突等。**V2+ 固件会顺利通过全部检查；V1 固件会在某一项上明确中止并说明原因。** 干跑不写盘，对固件没有任何影响。

> 固件版本与键盘外观并非一一对应，不存在可靠的外观判据 —— **以干跑结果为准**。

### 0.2 不要用 SHA-256 判断固件对不对

**每一台设备 Dump 出来的固件本来就不完全一样。** 512 KB 主 Flash 中包含设备独有内容：

| 设备独有内容 | 位置 |
|---|---|
| 蓝牙设备名称 | `0x21228`（ASCII `TrackPo` 开头） |
| 2.4G 无线 ID | `0x78054`（特征 `F3 FC` 之后的 12 字节） |

因此：

- **原厂固件的 SHA-256 因机而异** —— 拿别人的哈希来比自己的固件，必然不匹配，**这不代表你的固件有问题**；
- **补丁后固件的 SHA-256 同样因机而异** —— 因为改造只在固定地址追加逻辑，设备自己的身份数据原样保留。

实测结论：在两台设备上跑同一套补丁，**两个补丁产物之间仅 18 字节不同，且全部落在上述设备独有数据区** —— 也就是说**改造逻辑在任意设备上都是逐字节一致的**。

**正确判据**（按顺序执行）：

1. **补丁脚本的前置检查**（干跑）—— 校验固件结构是否符合本补丁的假设；
2. **验证脚本的结构性检查** —— 校验差异区间精确落在预期范围、其余字节逐字节未变、钩子与 trampoline 语义正确。

SHA-256 只在**同一台设备**上重复 Dump 的场景下有意义（用于确认 Dump 稳定、文件未损坏）。

> 读写固件需要**开启键盘电源**才能识别和读写，断电状态 J-Flash 无法连接芯片。

## 2. 硬件连接

1. 将 KC-1957 置于**关机模式**。
2. 用测试夹 / 杜邦线，把 J-Link OB 的以下三个信号接到主板对应测试点：
   - **GND**（共地）
   - **SWDIO**（数据）
   - **SWDCK**（时钟）
3. **VTref 不要连接**：J-Link OB 的 **VTref** 引脚建议保持悬空、不要接到主板。特别注意**严禁接入 5V**——若误将 VTref 接到 5V 电平，可能直接烧毁 J-Link OB 与 KC-1957 主板。SWD 通信仅需 GND / SWDIO / SWDCK 三根信号即可工作。
4. 接好线后，**打开 KC-1957 上电**（键盘进入可识别状态）。

> 连接时注意 GND 先共地，避免带电热插拔；确认测试夹接触牢固、无短路再上电。

---

## 3. J-Flash 工程配置

1. 打开 J-Flash，新建工程（**File → New Project**）。
2. 在 **Project settings（F4）** 中设置：
   - **Target Device**：`nRF52832_xxAA`
   - **Target Interface**：`SWD`
   - **Speed**：`Auto` 或 `1000 kHz`（1 MHz）
3. 点击 **Connect（F5 旁的连接按钮 / Target → Connect）**，状态栏应识别到 **nRF52832** 内核与芯片 ID。
   - 若连接失败，检查 GND/SWDIO/SWDCK 接触是否牢固、键盘是否已上电。

## 4. Dump（备份原始固件）

nRF52832 内部 Flash 分为两个需要保存的区段：

| 区段 | 地址范围 | 大小 | 内容 |
| --- | --- | --- | --- |
| 主 Flash | `0x00000000` – `0x0007FFFF` | 512 KB | 固件主程序、键位表、配置 |
| UICR | `0x10001000` – `0x10001FFF` | 4 KB | 用户配置寄存器（含部分出厂/配置信息） |

**操作步骤：**

1. 菜单：**Target → Manual Programming… → Read Back → Full chip…**
   - 读取整片（含主 Flash 与 UICR；FICR 工厂只读区无需单独保存）。
2. 菜单：**File → Save Data File As…**
   - 第一次：选择地址范围 `0x00000000` – `0x0007FFFF`，保存为 `KC-1957_orig_main.bin`（512 KB）。
   - 第二次：选择地址范围 `0x10001000` – `0x10001FFF`，保存为 `KC-1957_orig_uicr.bin`（4 KB）。
3. （建议）对两个文件计算 SHA-256 并记录：
   ```text
   # 示例（Windows PowerShell）
   Get-FileHash -Algorithm SHA256 KC-1957_orig_main.bin
   Get-FileHash -Algorithm SHA256 KC-1957_orig_uicr.bin
   ```
   > ⚠️ 该哈希**只用于确认自己重复 Dump 的结果是否稳定、文件是否损坏**。
   > 它**不能**用来判断固件版本是否正确、也不能用来和别人分享的哈希比对 ——
   > 每台设备的固件本就不同（见 [第 0.2 节](#02-不要用-sha-256-判断固件对不对)）。

> **务必先完整备份再做任何修改或刷写。** 这两个文件就是主板「原始固件」，是救砖的唯一回退手段。

## 5. 刷回固件（恢复 / 写入）

> **⚠️ 关键顺序：先抹除 → 再写入 → 最后校验。**
> 文档特别提示：某些情况下，若「完整擦除后未把额外的 4 KB（UICR）一并写回」可能导致异常。因此 UICR 区段**不能漏写**。

**操作步骤：**

1. **抹除（Erase）**
   - 菜单：**Target → Manual Programming → Erase**（整片擦除主 Flash 与 UICR）。
   - 等待状态栏提示擦除完成。

2. **写入主 Flash（512 KB）**
   - 菜单：**File → Open Data File…**，选中 `KC-1957_orig_main.bin`，在弹出的起始地址框填入 `0x00000000`。
   - 菜单：**Target → Manual Programming → Program**，将主固件写入。

3. **写入 UICR（4 KB）**
   - 菜单：**File → Open Data File…**，选中 `KC-1957_orig_uicr.bin`，起始地址填 `0x10001000`。
   - 菜单：**Target → Manual Programming → Program**，将 UICR 区段写入。
   - **注意**：不可只擦除主 Flash 而漏写这 4 KB，否则可能异常。

4. **校验（Verify）**
   - J-Flash 提供「写回并校验」一体化功能：在编程时可直接选用 **Program & Verify**（或 **Auto**），即写入完成后自动执行校验；状态栏显示 **"Verified OK"** 即通过。
   - 若分步操作，则在写入后单独执行 **Target → Manual Programming → Verify**（或 **File → Verify**），确认芯片读出内容与写入文件逐字节一致。

5. （可选双重确认）
   - 再执行一次 **Read Back → Full chip…**，把读出的主 Flash / UICR 与原始备份文件做二进制比对（如 `fc` / `cmp`），确保完全一致。

## 6. 注意事项与风险提示

- **必须上电**：读写任何操作前确认键盘已供电，否则 J-Flash 无法连接。
- **UICR 4 KB 不能漏写**：仅擦除主 Flash 而不恢复 UICR 可能引发异常。
- **先备份后操作**：任何改写（含键位 / 掩码修改）前，先完成第 4 节的完整 Dump。
- **共地与防短路**：GND 先接，确认无短路再上电；避免带电插拔 SWD 线。
- **修改固件内容**（如键位映射、有效键掩码、2.4G ID、蓝牙名称等）的具体地址位置，见第 8 节「固件关键信息位置」速查表。
- **排线与焊盘**：X220 排线分同面（"R"）/ 异面（"L"）版本；盘体薄膜金手指易损，尽量避免反复拆装。

## 8. 固件关键信息位置速查

> 下表地址均为 nRF52832 内部 Flash / SRAM 偏移（相对芯片地址空间）。任何改写前务必先完成第 4 节的完整 Dump 作为回退备份。

### 8.1 原始固件静态位置（读 / 改这些地址）

| 内容 | 地址（偏移） | 说明 |
| --- | --- | --- |
| 主 Flash 区 | `0x00000000` – `0x0007FFFF` | 512 KB，固件主程序、键位表、配置 |
| UICR 区 | `0x10001000` – `0x10001FFF` | 4 KB，用户配置寄存器；刷回不可漏写 |
| 有效键掩码（BLE） | `0x1E840` | 原始值 `FF7F7F…8F830BE7A64841`；改为 `FFFF` 可激活全部键位 |
| 有效键掩码（2.4G） | `0x4A6A6` | 原始值 `008080…707CF41C59B7BE` |
| 键位定义表（蓝牙 KEYTBL_BT） | `0x2CBF0`（长约 128 B，至 `0x2CC6F`） | 特征字 `351E142B04291D8B`；X220 / SL410K 适配即改此表 |
| 键位定义表（2.4G KEYTBL_G） | `0x4A6FA`（长约 128 B，至 `0x4A779`） | 同上特征字 |
| 行引脚表 ROWPIN | `0x2CBE0` | 行号 → GPIO 引脚映射 |
| 2.4G 无线 ID | `0x78000` 区段 | 特征 `F3 FC` 之后的 12 字节为 ID |
| 蓝牙名称 | 搜索 ASCII `TrackPo`（`54 72 61 63 6B 50 6F` / `547261636B506F69`） | 蓝牙设备名字符串 |
| 多媒体键定义（2.4G） | `0x4A6E2` | 2.4G 多媒体键数据 |
| 多媒体键定义（BLE） | `0x2CC78` | 蓝牙多媒体键数据 |

### 8.2 本项目 v5 / v6 MOD 注入位置（对照 / 回退参考）

| 内容 | 地址 | 说明 |
| --- | --- | --- |
| Trampoline 注入空洞 | `0x50000` – `0x504FF` | 5 段（`0x50000`/`0x50100`/`0x50200`/`0x50300`/`0x50400`），静态不可达，专放补丁代码 |
| Hook A（蓝牙扫描行循环） | `0x1E4E4` | 改 `nop`+`ldr` 为 `bl #0x50000`，驱动 Fn 状态 E0F |
| Hook B（2.4G 扫描行循环） | `0x41252` | 改 `bl #0x50100` |
| Hook C（2.4G P0.6 判定） | `0x411C6` | 伪键 `0xDF`→`0xE0`，改读 E0F |
| Hook D | `0x1EB74` | 改造注入点之一 |
| Hook E（蓝牙 HID 修饰字节） | `0x23A76` | 清零修饰字节并注入 Left Ctrl |
| Fn 状态变量 E0F | `0x20001E0F` | SRAM，去抖后「Fn 按下」；20 处引用 |
| 新变量 E0F2 | `0x20004800` | v6 新建，P0.6 去抖自用 |
| P0.6 去抖池槽 | `0x1B8A0` | 原指向 E0F，v6 改指 E0F2（断开 P0.6→E0F） |
| P0.6 电平读取 | `0x50000510` bit6 | P0.6 是否按下 |
| v6 键码表改动：KEYTBL_BT[100] | `0x2CC54` | `0x00` → `0xE0`（原 L-Ctrl 槽发左 Ctrl） |
| v6 键码表改动：KEYTBL_BT[120] | `0x2CC68` | `0xE0` → `0x00`（矩阵 r15c0 不再发 Fn） |
| v6 键码表改动：KEYTBL_G[100] | `0x4A75E` | 对称改为 `0xE0` |
| v6 键码表改动：KEYTBL_G[120] | `0x4A772` | 对称改为 `0x00` |

> 说明：8.1 为原始固件定位信息，8.2 为本项目已落地的改造注入点；回退时直接用第 4 节备份覆盖即可还原。
> 另：原硬件资料中还记录了 **2.4G 接收器（罗技 CU0008，用 CCDebugger 烧写）** 的对码 ID 三段位置（约偏移 `0x1921`/`0x1924`/`0x1923` 附近），属于另一颗芯片，地址体系与上方 nRF52832 不同，不在本表范围内。
